# 盯跑卡和后台派活（架构师读）

## 跑卡时要一直盯着

- 从建卡一直盯到卡“已合并”或“已放弃”：卡停下转人接手、等用户点按钮、监控到点，都要马上续上，不能关。用户点了“接受”“放进项目”后要靠监控接上下一步。（来历：11-20 用户“你不要把监控关掉，你需要监控着流程，你好对接起来”）
- 盯两样：卡片流转记录（交接、复查结论、停下、接受、放进项目）和干活的人本身（实时输出、副本里的文件变化）。
- 2 分钟没新输出 → 马上看；看到报错字样（429、Too Many Requests、Out of credits、402、No capacity），先确认是干活的工具自己报的错、不是它正在读的代码或测试里的字（限流测试里就有这些字），确认后立刻停卡换人；监控要过滤严，别把代码原文里的 error、401 当报错报给用户；没报错只是安静 → 等到 5 分钟（高档模型会先想几分钟）。写测试 10 分钟还一个文件没写出来要警觉。（来历：11-19 一个模型额度见底，18 分钟没写出文件才发现）
- 卡在等用户确认时没动静是正常的，不用提醒。
- 自己发现问题、及时汇报，不能等用户来喊；有要用户点的按钮，主动说清点哪个。
- 每张卡跑完记“流程观察”：各岗位照没照交代办、交接的话有没有丢信息或塞太多、每步耗时花在哪。

## 后台派活

- 命令末尾一律加 `< /dev/null`；启动后 30 秒内看一眼确认真在跑；再挂一个监控，进程结束或几分钟没新输出都要报。卡住时完成通知永远不来，不能只等通知。（来历：11-18 空等 20 分钟）
- 从后台启动开发助手的命令前面加 `env -u TZ`（这台机器终端的时区和窗口不同）；给用户报时间按北京时间。卡片记录只记运行时长，不记钟点。
- 派活要并行：基线测试和写测试同时跑；每一棒干活时提前写好下一棒的施工单；进度消息只在交接、出错、要拍板时发。（来历：11-17 用户“整个过程很慢，效率很差”）
- **能开的卡先开，不排队**：一批卡里，施工单复查过了、又不依赖别的卡还没放进项目的代码，就马上建卡开跑，不等前面的卡放进项目。只是改到同一个文件不算依赖——放进项目时 git 多半能自动合，撞了由后放的那张手工合。程序只拦“同时两张在施工”：前一张到了待验收、等看页面，下一张就能开。真依赖（后一张要用前一张新加的功能、数据或口径）才排在前一张放进项目之后，见《方案怎么写》“大活怎么拆”。（来历：11-26 train 体验升级，Claude 怕共用文件撞车，把已过复查的卡 3 压着等卡 5 放进项目，开发助手白等约 50 分钟；用户：“如果有已经通过可以开工的就先开工，只要是可以独立不关联其他任务的都可以，这样可以提升效率啊”）

## 平时走前台，特殊时期走后台

- 平时：施工单写好后，把“粘给行政的话”给用户，用户粘给行政、点确认、批准开工。
- 用户外出、睡觉或明说时：自己用命令建卡、开跑、盯卡、停下接手、验收。放进项目、本机提交照那次的实际授权办（比如用户说“验收过的自己放进项目、本机提交”，就不再逐张请示）；推送、删用户数据、超出已批方案仍要用户。命令：`python3 -m collab new-card / plan / approve / run / merge`（用装好的应用里那份代码跑，并用应用自己的启动方式，窗口里才看得到）。
- 授权只对那一次有效；每隔几张卡留一张走前台，前台坏了才发现得了。
