# 范围变更和测试不弱化（架构师读）

## 施工中发现要改的超出已批范围

比较的基准：大、中需求看《方案》；小需求看台账里那一行“已对齐的范围 + 验收条件”（小需求开工前先留这一行）。

1. **先停下**，不顺手改；
2. 登记：大需求 → 《任务清单》末尾“施工中补充”；中需求 → 《方案》末尾同名一节；小需求 → 原台账条目下追加。写改了什么、为什么、**怎么撤**；
3. 标“待你确认”，下一次汇报里单独列出，不要等用户来问；
4. 只有不改变任何行为的文字、注释同步可以顺手做，也要登记；
5. 做着做着变大了：先重新判大小，再补相应文档和批准。

登记格式：

```
| 编号 | 改了什么 | 为什么 | 怎么撤 | 状态 |
| S1 | ______ | ______ | ______ | 待你确认 |
```

（来历：“去掉老调度层”那次是先改了再登记，所以立“先停下”）

开发助手里干活的 AI 改了允许范围外的文件，程序一律撤销（不是让人选怎么处理）。

## 测试不许为了变绿而弱化

- 改老测试，只改**因需求变化而必变**的断言，逐条登记“改了什么、为什么”；
- 不许跳过测试、不许把断言放宽成接受退化；确实要跳过，要用户点头并写明失去了什么覆盖；
- 施工方报测试不合理时，由写测试的那一方（架构师）核对并改，不由施工方自己改。

（来历：曾把一套检测的 6 个测试跳过、另 2 处断言改成接受退化，复查指出后才撤销）
