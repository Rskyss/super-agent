# 复查、验收和测试节奏（架构师读）

## 四件事分清

| 事 | 谁做 | 说明 |
|---|---|---|
| 自测 | 施工者 | 先写测试、写完跑通；不算验收 |
| 独立复查 | 大、中需求：Codex 极高档（换人）；小需求：轻量复查 | 看够上下文、能跑测试就真跑；只读 |
| 修复 | 开发助手流水线内：测试没过自动返工（最多 3 轮），复查不通过自动退回（最多 2 次，还不过停下转人接手）；你自己写的：先核实复查意见再修 | 修完再复查 |
| 最终验收 | 架构师 | 全量测试、真实窗口走查、逐条核实复查结论；不能代替独立复查 |

**施工单也要复查**：中、大需求的施工单开工前先交 Codex 极高档复查，通过了才给用户粘贴的话（《施工单怎么写》第八节）。

**谁写谁不验**：你亲自写的代码（和文档），不论大小，都交没参与的模型复查（大、中交 Codex 极高档，小交 Codex 中档或新开的代理）。模型给自己打分会偏高。

## 验收要用真实工具

- 写施工单之前，先用真实工具试跑一遍关键流程，确认做法走得通；验收时再跑真实的写代码、写测试工具走一遍，不能只看假工具下的测试结果：假工具全过、真实环境照样会挂。（来历：11-06 第一批假工具全过、真实环境必失败）
- 写测试别禁得太宽，不要假设工具没有自动重试；假工具要和真实服务一样严格。
- 查施工方的汇报里“和施工单不一样的地方”，以及它有没有动旧测试。

## 复查轮数

- 施工单开工前那段复查另算，规矩见《施工单怎么写》第八节；下面说的是施工完的复查。
- 最多 3 轮“复查 → 修”。计数单位开工时登记：大需求按整份需求，中需求按这份方案，小需求按这条台账记录。返工不另起计数。
- 第 3 轮之后：
  1. 只剩轻微 → 默认记遗留，进最终验收；确实要改的，改完标“未经独立复查”进验收，并在汇报里告诉用户；
  2. 还有严重或中等 → 停下问用户；
  3. 为通过而做的严重/中等修复 → 补一次只看该修复的确认复查（不计入 3 轮）：确认通过进验收；确认仍不通过停下问用户，不再循环；确认复查可以报告这个修复本身带来的新问题，无关的新问题记遗留。
- 严重问题本轮必须修，不过夜。
- 问题分轻重、会不会退回，接手和最终验收时也照《复查分级》“程序怎么判退不退回”那一节办（包括“测试写错、安全或丢数据一律要修”），按它记以后再修的不追着修。
- 复查只为正常使用会碰到的问题开新一轮；边角情况记已知取舍。
- 同一个角落第二轮还在冒新问题：砍掉这一层，或改成从根上管的简单规矩，不继续一条条补。

## 复查意见先核实再改

逐条对着代码或记录核实，分三类：
1. 成立且本次修：改，补测试；
2. 成立但属范围外（改动前就有）：不改，记遗留，写明理由；本次新引入、按《复查分级》会退回的必须修；
3. 不成立：写明理由，不照改；但顺着它的怀疑方向再查一遍。

盯卡时发现复查意见反复出现或互相矛盾，叫停并核实，程序不会自己识别这种情况。

## 后台叫 Codex 复查

- 命令末尾加 `< /dev/null`，否则它卡在等输入；启动后一两分钟内确认真在干活（看它的会话记录在写）；复查用只读，不联网。
- 复查交代写清：需求和方案在哪、这次改了什么、重点查什么、第几轮、上轮提了什么。

## 测试节奏

| 什么时候 | 跑什么 |
|---|---|
| 修改轮 | 只跑和这次改动相关的测试 |
| 第一次交付前 | 全部测试 |
| 复查后的修改轮 | 只跑本任务和相关的；改到共用文件才全部 |
| Codex 判通过前 | 全部测试，所有大小都一样 |
| 最终验收 | 全部；上次全部之后代码、测试、配置（包括没提交的改动）都没变才能复用那次结果，并记下它对应的代码状态（哪个提交） |
| 提交前、发版前 | 全部，用 Python 3.15（装好的开发助手就跑在它上面；11-18 用户定不再要求 3.9） |

- 代码定稿后才开全部测试；跑的时候别改文件，改了那次结果作废。
- 全部测试用项目自带的分组并行（`collab/fullrun.py` 的 FullRunner：每个测试文件单独进程、几个同时跑、藏起真实 AI 工具），约 3～4 分钟；不要自己写顺序跑的脚本（要十几分钟）。
- 汇报关卡清单时照实写跑的是哪一档。
（来历：11-08、11-11 用户定“按开发进度把控全量测试”）

## 看不见的改动怎么验收

AI 规则、流程文档、跑卡程序的内部检查：拿真实证据（测试、真卡记录）判定，有提升、没问题就在台账写 ✅ 和依据。看得见的（界面、用户操作流程）仍要用户亲自看过。

## 岗位试用期（11-19 用户定）

- 写测试、写代码、复查三个岗位：一个模型第一次上某个岗位（或换岗、出新版本），头 3 张卡算试用。
- 看：交成率（服务限流单独记）、平均用时、复查挑出它的问题（尤其自己加没要求的东西、测试写错、改坏旁边、为迁就测试改产品）、要不要人接手收拾。数据在 `docs/流程数据/`。
- 写方案、备交接资料是后台作业：有施工单时不用，没施工单时固定用 Codex 低档，不走试用。
- 试用期满在 `docs/流程数据/点评记录.md` 的“复盘”里写结论，报用户定：通过 → 团队设置里这个岗位用它，写进点评记录的“各岗位模型”；不通过 → 这个岗位不再用它，写明原因，以后它出新版本可以再试。中途出大问题（连续两张卡要人接手、改坏老功能）可以提前结束，同样报用户。
