# 方案和任务清单怎么写（架构师读）

## 《方案》（`docs/任务名/方案.md`；中、大需求必写）

- 全文用产品语言：先写“做完后用户能感受到什么”，再写做法。
- 照《架构师》的三条原则：规则放必经处、和现有做法同构、“不受影响”附证据。
- 每个要做的东西写明来源：用现成的 / 改现有的 / 新做（写清为什么现成的不行）。
- **必须有“泼冷水”一节**。
- 中、大需求必填**影响面清单**（见下）。
- 涉及互相配合的模块 ≥3 个、后台任务、对接外部服务时，末尾附“技术设计”一节，写给下一个接手的 AI 看（用户可跳过）；施工中架构真变了，回来改。
- 中需求：开头写“需求复述 + 口径”，用户批方案就是批口径。

## 影响面清单（照抄填写，放进方案）

```
## 影响面清单
1. 动的是什么？   关键词：______  全仓搜到 ___ 个文件（代码 / 测试 / 页面文字 / 外壳 / 配置 / 文档 / 规则包）
2. 谁在读、谁在写？ 逐处：______ → 要跟着改 / 不用改（理由 + 搜索证据）
3. 有几个入口？   ______；规则放在必经处了吗：是 / 否（放在哪）
4. 会连带变什么？ 文档：__ 测试：__ 界面文字：__ 台账：__ README：__ 规则包：__
5. 和已批准文档矛盾吗？ 对过：共识 / 方案 / 台账口径；结果：无 / 有（停工→提出修订→用户批准→再动手）
6. 老数据、老配置、已装应用？ 兼容：__  重装：要 / 不要  影响正在跑的卡：有 / 无
7. 这次明确不改什么？ ______
8. 怎么证明做对了？  测试：__  走查：__（还没做的写“未做”）
9. 有没有奇怪的老代码？ 有 / 无；有的话：在哪 __  来历（哪次改动、为什么）__  决定：删 / 留（查不清就留，写“来历不明”）
```

- 第 2 问做不到逐行核实就照实写“按文件归类，没逐行核实”。
- 第 9 问来历：前一个 AI 留下的防坑代码，后一个看不懂就删、改乱（借鉴 pstack，11-18 用户批）。
- 真实例子（含当时漏掉的地方）：`docs/开发流程规范/开发流程规范.md`“影响面清单的真实例子（11-17）”一节。

## 《任务清单》（`docs/任务名/任务清单.md`；大需求必写）

- 一张表：编号 | 做什么 | 怎么验收 | 依赖谁 | 状态。交开发助手的项按依赖顺序排，后一张等前一张放进项目才开（见下面《大活怎么拆》）。
- 每项都要有能单独验证的验收标准；拆不出来，说明共识没写清，回去补。
- 写明展示节点（做到哪几项停下给用户看）。
- 写明复查计数单位：大需求按整份需求算 3 轮；拆成几张卡逐张交付的，按《大活怎么拆》改成每张卡各算。
- 交给开发助手的项，同时写施工单（《施工单怎么写》）。
- 末尾留“施工中补充”一节，范围变更登记在这（《范围变更》）。

## 大活怎么拆（交开发助手前判断）

一张卡塞太多，复查会一轮轮收不住；拆成几张能单独验证的卡，每张收得住，也不会做到一半停在分支上没人收尾。拆不是为了省时间：去掉下面四张大卡和已放弃的 CARD-009 后，其余 16 张卡平均干活约 42 分钟、复查退回约 1.6 次，拆成三张总时间可能比一张更长。

**判法**（写施工单时逐条对）：
1. 施工单第三节里有能单独做完、单独验收的几块（做完一块就能测到一块）→ 拆。
2. 同一张卡既改跑卡流程的核心，又改界面、行政等别处 → 拆，但按“完整操作”切，不按层切：用户点一下就走完的一整件事（比如“接受剩下的问题”：后台跑全部测试、等待时显示状态、全过进待验收），核心和界面要放在同一张卡里，不能先改按钮行为、下一张才补等待显示。拆完每张都要满足下面“怎么拆”第一条，满足不了就不拆，在判断里写明。
3. 改动量明显超过近来的普通卡 → 不单凭这条拆，但要在判断里写清为什么不拆。参照：C1、C1.5、C1.6、全量卡（CARD-003、004、005、010）都是新增上千行（含测试），干活 85～187 分钟、停下转人工 1～3 次，四张合计占 21 张卡全部干活时间约四成、已记录 token 约四成。
- 例外只有一种：改的文件多，但每处都很机械（CARD-018 换旧名，改了 10 个产品文件，9 分钟一次过）。这个例外只抵消“文件多”，抵消不了第 1、2 条。文件数本身不作判据（CARD-017 只改 2 个产品文件，照样退回 2 次、转人工）。

**判断写在哪**：中需求写在《方案》里一行“拆不拆：拆成 N 张 / 不拆，理由……”；大需求写在《任务清单》。每张施工单开头的引用块里写一句“拆卡判断：本单是第 i/N 张，前一张是……”或“不拆，理由……”，开工前的 Codex 复查照这句核对。

**怎么拆**：
- 每块放进项目后项目都是能用的完整状态，不留半成品；每块一张施工单、各自的验收测试。
- 按依赖排先后，被依赖的先做。**有依赖的，后一张等前一张“已合并”（放进项目）才开始下面的顺序**；互不依赖的（只是改到同一文件不算）复查过了就开，不排队，见《盯跑卡》“能开的卡先开”。卡的副本是第一次点开工时才从项目当时的最新提交分出来的；前一张只到“待验收”就开下一张，副本里没有前一张的改动。
- 后一张的顺序：前一张放进项目 → 按实际结果核对后一张的施工单 → 把后一张的施工单和验收测试提交进项目（只提交本卡的，不提前存再后面几张的，免得挡住放行）→ 自查 → Codex 复查施工单（《施工单怎么写》第八节）→ 复查期间和复查后改过的施工单和测试再提交一次 → 给粘贴的话 → 用户建卡、开工。施工单可以提前写好，测试不提前提交。
- 一个项目同一时间只能有一张卡在施工（程序拦着，第二张点开工会提示“已有一张卡在施工”），所以有依赖的卡只能一张接一张；互不依赖的，前一张到待验收就能开下一张。

**复查轮数**：开工前的施工单复查照旧每张单独最多 3 轮（《施工单怎么写》第八节）。施工后，程序每张卡自己的自动退回照旧；接手和最终验收时你叫的独立复查，拆开交付的按**每张卡各算最多 3 轮**（《复查和验收》“复查轮数”已写这条例外）。计数单位登记在：大需求《任务清单》，中需求《方案》里那行“拆不拆”后面。

**同时跑**：现在做不到（见上一条程序限制），不要在任务清单里安排。

（来历：11-20 借鉴 pstack 第二轮 P0。用户先提“程序自动拆、多队并行，加回一层专管分派的角色”；Claude 核对 21 张卡的数据后说明：最收不住的四张大卡改的都是跑卡流程同一处，并行会撞；自动拆等于让模型一次写几份可能没写死的施工单。用户选“由架构师拆、Codex 复查施工单时判该不该拆，不加新角色”。Claude 当时说“程序允许两张卡同时跑”，Codex 复查查出程序其实只许一张卡在施工、有测试守着，是 Claude 看漏了；用户 11-20 定删掉同时跑，只留拆卡和依次交付。）
