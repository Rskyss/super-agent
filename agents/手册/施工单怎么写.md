# 施工单怎么写（给写施工单的人：产品经理 / 架构师，不管哪个模型来当）

施工单是交给开发助手的唯一交接物。写测试、写代码、复查的模型只看施工单和代码，看不到你和用户的聊天。施工单没写死的地方，它们只能猜；猜错就被复查退回，一轮轮改，越改越乱。

照《施工单模板》抄一份填。下面是每节的要求和为什么。

## 一、必备几节（标题里的关键词程序要认，不要改字）

开发助手“写方案”那一步会按标题关键词直接从施工单里摘内容：

| 节 | 程序怎么读 | 缺了会怎样 |
|---|---|---|
| `## 一、要做什么（一句话）` | 取第一段当摘要 | 摘不出，写方案失败，右栏说明缺这一项，卡停在待对齐（11-26 起不再改由模型重新拆） |
| `## 二、允许改哪些文件` | 每行 `- ` 开头、路径用反引号包住，**一行只写一个路径**（一行写两个，程序只认第一个）；`**不许改**` 那行之后不算 | 同上 |
| `## 三、具体做法` | 每个 `### ` 小标题算一步 | 步骤只剩一句“照施工单做” |
| `## 六、不做什么` | 取第一段 | 写成“照施工单” |
| `## 八、验收` | 找 `验收命令：` 后面反引号里的一条命令 | 同第一行 |

另外四节程序不读，但模型要读：`## 四、状态表`、`## 五、原有行为清单`、`## 七、老测试`、`## 九、粘给行政的话`。它们的标题里不要出现“要做什么”“允许改”“做法”“不做什么”这几个词，免得程序认错节。

## 二、状态表（凡是“记住状态、切回恢复、几处共用同一份数据”的功能必填）

一张表：| 什么时候 | 谁的东西 | 存什么 | 恢复成什么 / 显示什么 |。下面几种情况每种都要有一行，不适用的写“不适用”：

- 正常情况；
- 页面或数据还在加载时；
- 正在看别的东西时（比如看卡时，主对话里没发的字归谁管）；
- 删掉之后；
- 切到一半又切走；
- 退出应用时。

来历：CARD-019（切换项目）施工单只写了“存对话、卡片、草稿，切回恢复”。三轮复查退回的十几条，几乎全落在加载先后、两个对话共用一个输入框、切到一半又切走、退出时补存这几种情况上，写代码的只能边被退回边猜。

## 三、原有行为清单

列出这次改动会碰到、但必须保持不变的老行为（用户看得到的），每条一句话，后面写现在由哪个测试守着；没有测试守的写“没有”，并在验收测试里补上。

- 写代码的修退回问题时，碰到清单里的行为会停下、写进汇报，不擅自改。
- 复查员发现清单里的行为被改掉，标严重。

来历：CARD-019 写代码的为过复查，把“进团队设置页收起右栏”这条老行为改掉了。施工单只写了“只按施工单做”，没挡住。

## 四、测试怎么写

- 在“验收”一节写明测试写法：页面行为用实跑页面的检查，见《测试怎么写》。
- 验收测试由写施工单的人先写好、放进项目，施工方不许改；写测试的只补充，写进施工单指定的新文件。新测试的文件名要在“允许改哪些文件”里（CARD-019 复查就抓到新测试文件名不在允许范围）。
- 写施工单的人自己写的验收测试也照这条。CARD-019 的验收测试是逐字比对代码，起了坏头。

## 五、老测试

- 写验收测试前，全仓搜跟新口径冲突的老测试，不只看同名的验收文件。列进“老测试”一节：哪些会变、为什么。施工方不许改老测试。（来历：11-18 token A2 只改了 2 条，漏了 9 条，写测试的被退回又不能改测试，白跑一轮）
- 几张卡排队时，下一张卡的验收测试等前一张放进项目后再存进项目（存完自查、交第八节的复查、通过后给粘贴的话），不要提前存后面几张的。（来历：11-20 先存了第三张卡还不过的测试，挡住了第二张卡放行前的全部测试）拆开交付的几张卡也一样：一张接一张，见《方案怎么写》“大活怎么拆”。互不依赖、已经开跑的卡，开工前提交本卡的验收测试。Python 项目（逐文件跑）照旧：卡里跑全部测试时程序会和改之前比，别的卡还不过的验收测试不算这张卡改坏的（collab/dispatch.py）。另外都可以（项目配了自己的全部测试命令的网页项目更要）在提交时**当场登记进已知没过名单**：`collab known-fail add <项目> --file 测试文件 --card 本卡 --why 原因`（只能登记整个文件）。全部测试没过时，程序在副本里把名单里等卡的测试文件拿掉、原样再跑一遍，拿掉后全过就不算这张卡改坏；卡住后点“接受”时也一样；本卡放进项目时程序自动撤掉这几条。所以等卡的验收测试要单独放一个文件，别和老测试写在同一个文件里，也别被别的测试引用、别改全局状态（拿掉后老测试的行为会跟着变）；全部测试命令也不要按某个文件在不在改变跑的范围，也不要在命令里自己指定缓存目录。（11-27 卡 B2′）（11-26 补）**例外**：下一张卡预改的老测试，如果也在正在跑的卡的验收命令里（放进项目时会在主目录重跑这条命令），就先别提交、放进项目前还要从主目录收起来，等正在跑的那张放进项目后再提交。（11-26 train 卡 4 预改的 process-worksheets、final-composite-score 也在卡 3 验收命令里）

## 五之二、走查（改界面的卡必填）

程序跑卡时，写代码的交活、本卡测试过了以后，会跑施工单“验收”一节的**走查命令**：在后台浏览器里按真实窗口三栏的宽度把页面点一遍、每一步截图，截图放进卡片文件夹，复查员照“走查步骤”表逐张对照设计图。走查命令跑不通（点不到、打不开）就像测试没过一样退回写代码的。（P1 卡 A 放进项目前，程序还不会跑走查命令，写了也只是给复查员看。）

- **谁写**：写施工单的人，和验收测试一起写好、提交进项目；施工方不许改，写进“不许改”。走查脚本放 `tests/walk_<任务名>.py`。
- **怎么写**：用开发助手项目里的走查工具 `tests/walk_tool.py`（用法写在它开头），样板是 `tests/walk_example_card021.py`。要打开某张卡，卡片资料放 `tests/fixtures/walk_cards/<卡号>/`（.collab 不提交，卡片副本里没有，不能从 .collab 取）；复制老卡资料时只拷需求卡、方案、状态、流转记录这几样，不拷“流转/”文件夹和日志，拷完搜一遍有没有本机路径和密钥。
- **步骤表和设计图对上**：施工单“走查步骤”表每一行对应脚本里一次截图（`w.shot(...)`），步骤名一字不差；每步写一句“做对了页面上一定有的字”（`expect`，看不到就算走查没过，防止截到一张没加载出来的空页），**写短、写同一行里的几个字**（工具判“截图里看不看得见”有两种像素级边角判不准：一行字只被裁掉下半截仍算看见；遮挡物只挡住跨行处的空格会误判看不见。写短的单行字碰不上）；有设计图的那步写清对照哪一张（项目里的相对路径）。设计图只是草图：对照结构、内容、文字、按钮、状态，不抠像素。
- **哪些情况走查会算没过**：点不到、等不到的东西（5 秒）；expect 的字没出现、或被收起框挡住截图里看不到；页面脚本报错；页面向后台要数据时后台回了错误或连不上。
- **走不了的步骤**：左栏点卡片、切项目、菜单这类要交给 Mac 外壳处理的点击，后台浏览器里点了没反应。用走查工具的“直接打开到这张卡”代替：左栏用 `open("nav", card=卡号)`，右栏用 `open("panel", card=卡号)`，中间用 `open_card(卡号)`，不要模拟点击。
- **待验收的卡**：要截“等你确认”的样子，复制卡片资料后把状态改成待验收即可，走查工具会在假项目旁边建好卡片副本文件夹。
- **交出前自己跑一遍**：功能还没做，走查多半会在新加的那一步点不到——这是对的，和新测试先不过一个道理；但前面已有的几步要能走通、截出图。跑不通的地方要么是脚本写错、要么是假数据不够，交出前改好。
- **不调模型、不碰真实设置**：走查工具起的后台服务用临时设置，干活工具和钥匙串命令都换成了一跑就失败的假的；脚本里不要自己去读用户的设置、不要联网。
- **跑走查要的环境**：本机 Chrome，和给跑卡用的那份 Python（Homebrew 的）装好 playwright；换电脑要重装。
- **没有走查命令、靠人看的卡**：“验收”一节写一行 `- 走查：放进项目前要看页面：……`，复查通过后卡会停在“等看页面”。写了要做的事就会停；不用看的明说“走查：不涉及”。（来历：11-25 train 三张施工单换了说法，程序一张都没认出来）
- **其他项目**：走查工具现在只有开发助手项目有；超级玩家第一次做界面卡时，照它复制一份再调。
- 自动走查截图**不能代替**真实窗口走查：后台浏览器是三栏分开截、用 Chrome，和真实窗口的苹果网页引擎、三栏拼接可能有细微差别；最终验收照《真实窗口走查》在真实窗口看。

（来历：11-21 P1“交活自动附走查截图”，用户批准；11-16 超级玩家界面和设计图对不上，被用户退回）

## 六、粘给行政的话

用户会把这一段原样复制粘给开发助手的行政建卡。行政看不到你们的讨论，只看到这一段，而且它是便宜的模型。所以：

- 自成一段，不写“见上面”“同前”；用词具体直白，不留需要它去猜的话。
- “允许改哪些文件”只写路径，路径后面不加括号备注（“只加一行”这类要求写进施工单正文）。行政会照抄进卡片的允许范围；程序现在会去掉行尾备注，但别依赖它。（来历：CARD-020 写了“panel.html（只加一行）”，程序把整串当文件名，写代码的改动每轮被当越界撤掉，白跑 3 轮）
- 写在施工单末尾，也原样写在发给用户的聊天消息里（放在一个框里）。
- 需求中途变了，重新给一段新的，不让用户自己改旧的。
- 格式固定：

```
按施工单做：<施工单路径>
要做什么：<一两句>
不做什么：<一两句>
怎么算做完：<可检查的条件>
允许改哪些文件：<逐条>
验收命令：<一条命令>
```

## 七、交出前自查

假装自己是只看施工单和代码、不聪明的模型，逐条问：

1. 有没有哪一步要它猜？（“恢复”恢复成什么？“加载中”显示什么？页面上显示的字从后台哪一项来、是全文还是摘要？——CARD-020 没写清“全文从哪来”，写测试的假数据给了摘要，逼出拼旧说明的写法，复查退回两轮）
2. 这次是记住状态、切回恢复、共用数据的功能吗？是的话，状态表每种情况都填了吗？
3. 原有行为清单列全了吗？每条有测试守着吗？
4. 验收命令自己跑过吗？要求的功能还没做，所以新测试应该不过、老测试应该全过——确认是这样。验收命令一律写成 `python3 -m unittest discover -s tests -p "<测试文件名>"`，多个文件用 `&&` 连起来；不要写 `python3 -m unittest tests.xxx`——本机装着一个同名的 tests 包，这种写法会直接报“找不到模块”。（来历：11-20 规则包第④步第 2 次试写，照 README 里的旧例子写成了 tests.xxx，本机跑不起来）
5. 允许改的文件够窄吗？新测试的文件名在里面吗？一行只写了一个路径吗？（来历：11-20 写第一张新施工单时发现，一行写两个路径程序只认第一个）
6. 粘给行政的话离开聊天也看得懂吗？

## 八、开工前先交 Codex 复查（中、大需求）

中、大需求的施工单（连同已经放进项目的验收测试）自查完，**先交 Codex 极高档只读复查一次，通过了才把“粘给行政的话”给用户**。小需求不用。

复查员看这几样：有没有要施工方猜的地方；状态表、原有行为清单全不全，每条老行为对的测试对不对；跟新口径冲突的老测试搜全没有；施工单承诺的效果，按它指定的做法和允许改的文件做不做得到；和规则包里已有的口径（比如进度说明不显示路径）有没有冲突；验收命令跑不跑得起来；改界面的单子写了走查命令和走查步骤没有、步骤和设计图对不对得上、走查脚本交出前跑过没有；施工单开头的“拆卡判断”写了没有、对不对（照《方案怎么写》“大活怎么拆”的判法逐条对，该拆没拆算中等问题）；是拆开的第 2 张以后，前一张放进项目了没有（有任务清单的连任务清单一起交给复查员）。

测试证据只看开工前该有的样子：验收命令跑得起来、新测试按预期不过（还没施工）、老测试全过。不跑全部测试，全部测试照施工完以后的节奏。

不通过：先核实再改，改完再查。

**通过后先提交再给粘贴的话**：复查期间改过的施工单和验收测试，再提交一次进项目，确认项目最新提交里就是通过复查的那一版。卡的副本是第一次点开工时从项目最新提交分出来的，没提交的改动副本拿不到，施工方会照着初稿干。第一张卡也一样。（来历：11-21 P0 第 3 轮复查指出；C1.6 就有过复查后同时改施工单和测试）
- **每张施工单单独计数，最多 3 轮**；不占这份需求施工完那段复查的轮数，几张施工单之间也互不占。
- 第 3 轮后还有严重或中等：**停下问用户，不给粘贴的话**。这张卡先不开的话，把已经提交的本卡验收测试撤出项目（再提交一次去掉它），免得挡住别的卡放行；之后要开再存回来。
- 第 3 轮后只剩轻微：照改，或写进施工单让施工方知道；改完照上面“通过后先提交再给粘贴的话”再提交一次，然后给粘贴的话，并在汇报里告诉用户剩了什么。
- 这一段不走《复查和验收》“第 3 轮之后”那几条（那是施工完、进最终验收用的）。

（来历：11-20 规则包第④步试写，GLM-5.3 写的施工单有 4 处中等问题：漏查会冲突的老测试、行政失败时显示什么前后矛盾、承诺“展开看原文”却按它的做法做不到、漏了“不显示路径”。按原来的流程，要施工完复查才发现，每退回一次约 25 分钟。用户 11-20 定：中、大需求开工前先交 Codex 复查。）
