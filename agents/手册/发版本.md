# 发版本和推送（产品经理、架构师读）

版本号是给用户看的里程碑，提交记录是给开发看的施工日志，两回事。

## 版本号：`v 大版本 . 功能版 . 修复号`

- 能用一句“现在你可以……了”说出来 → 功能版 +1，修复号归零。
- 都不是（修问题、收尾、优化、加固）→ 修复号 +1，例如 `v0.91` → `v0.91.1`。修复号只用数字。
- 修复号为 0 时不写出来。
- 开发助手现在的编号：v0.1～v0.9 之后是 **v0.91、v0.92……v0.99**，不写 v0.10（看着像 v0.1，比 v0.9 还小）。到 v0.99 时满足 1.0 条件就切 v1.0，不满足先补条件，不续成 v0.100。只剩 9 个功能号，升功能版要卡严。（来历：11-20 编成 v0.10 推上去，用户以为版本倒退，改名为 v0.91）
- v1.0 不是功能够多了，是敢对外承诺了：陌生人投入真实工作在上面，出了问题兜得住。

## 推送纪律

1. **推送、发版都是对外动作，每次先问用户**；用户这次明说了才推。
2. **一个版本＝远端恰好一个提交**：推送前把本机零碎提交合成一个，标题 `vX.Y 一句话主题`；正文第一段固定是“解决问题：1.～n”（每条一句：用户之前遇到什么 → 这版之后怎样），之后按“新增功能 / 优化功能 / 修复 bug”分组。合之前在本机另存一份原样（`backup/pre-vX.Y-squash` 分支），合完比对内容一字不差。
3. **推送前收尾做完**：台账、验收记录、使用说明（README）里的版本号文案全进这一个提交；严禁推完再补零碎提交。
4. 推前扫一遍有没有密钥；密钥只放 `.env`，永不进代码和提交。
5. 不发版就不推主分支；要跑远端检查就推临时分支。
6. 开发助手推到 GitHub 的 `dev-assistant` 分支。
