# 四道关卡和底线（所有角色）

这份规则来自 vibe-workflow：每一步都要留下看得懂、查得到的记录。口头说的不算，只有写进文件的才算。

## 一、四道关卡，顺序不能换、一道不能跳

1. **对齐**：任务卡片写清楚、方案经用户批准，才能开工。
2. **施工**：先写测试，再写代码。一次只做一件事，做完验证再做下一件。
3. **自测**：测试员交的是能说明要求、此时还不过的测试（功能还没写）；开发员交活时，本卡测试必须全部通过。过没过由程序真跑测试判定；项目支持时程序还会跑全部测试，配置了页面检查时也会跑；真实窗口走查由最终验收的人做。没跑到的检查，在回复里如实说明，不要说成已验证。
4. **登记**：台账、归档由程序在施工结束后补写；你在回复里如实写清做了什么、没做什么、卡在哪。

## 二、修问题时先过“三问”

修 bug 之前，先回答：
1. 问题出在哪一层？同类问题系统里还有没有别处？
2. 现在必须改，还是可以先不改？可以不改的，写明理由，不顺手改。
3. 修法和现有结构一致吗？不要为单个问题发明新机制。

修问题时，测试要先重现用户看到的问题：测试员交活时这条测试必须是不过的，开发员改好代码后才变成过。

## 三、别把项目越改越乱

后面接手的 AI 往往只看眼前的文件、照抄最近的写法；前一个 AI 留下的东西，后一个看不懂就会改乱。所以：

- 改之前先看清这次要改的东西还有谁在用；项目里已有现成做法的，照现有做法改，不另起一套。
- 看起来多余或奇怪的老代码，可能是前人为了防坑留的。没查清来历（用 git log 查是哪次改动加的、为什么）不许删；查不清就留着，在回复里写一句。
- 没帮上忙的改动要撤掉：一种改法没解决问题，先撤干净再试下一种，不要把“可能有用”的代码一层层叠上去。
- 新加的防护要有测试守着：只留一句注释提醒别删，后人照样会删。
- 代码里留提醒（临时、兼容、先这样），要写清为什么留、什么时候可以删。

## 四、记录放在哪里

- **总台账**（项目的 docs/开发进度跟踪.md）：按时间只追加，记每个关卡的结果，由程序补写。
- **卡片文件夹**（.collab/cards/卡片编号/）：需求、方案、执行记录（谁做了什么）、测试结果（每轮都保留）、返工记录、汇报。
- 只追加、不改写历史。发现记错了，追加一条更正，不删旧记录。

## 五、几条底线

- 测试员先写测试，开发员再写代码。
- 密钥、密码只放在 .env 或配置文件里，不写进任何记录或提示词。
- 推送、合并、发版，都由用户决定，AI 不擅自执行。
- 只改任务卡片“允许改动的范围”里列出的文件。范围外的改动（包括临时脚本、草稿、汇报文件）会被程序直接撤销，白做。
- 不要提交（commit）、不要合并、不要推送；这些在用户点头后另行处理。

## 六、所有人都要知道的

- 会有看门人盯着动静（副本里的文件变化，或你的输出还在涨），连续 15 分钟都没有会被判定为卡住并停止；5、10 分钟没动静时行政会告诉用户。遇到需求看不懂、环境跑不起来，直接在输出里写清楚卡在哪，不要原地空转。
- **只跑本卡的测试**：派活时会写明本卡的测试命令，要确认就只跑这一条，不要跑全部测试（全部测试留到最后验收）。写测试的只改测试文件，改了原有的产品代码会被撤掉。
