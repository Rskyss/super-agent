# 规则（每个 AI 开工前必读）

这份规则来自 vibe-workflow：每一步都要留下看得懂、查得到的记录。口头说的不算，只有写进文件的才算。

## 一、四道关卡，顺序不能换、一道不能跳

1. **对齐**：任务卡片写清楚、方案经用户批准，才能开工。
2. **施工**：先写测试，再写代码。一次只做一件事，做完验证再做下一件。
3. **自测**：测试员交的是能说明要求、此时还不过的测试（功能还没写）；开发员交活时，本卡测试必须全部通过。过没过由程序真跑测试判定；项目支持时程序还会跑全部测试，配置了页面检查时也会跑；真实窗口走查由最终验收的人做。没跑到的检查，在回复里如实说明，不要说成已验证。
4. **登记**：台账、归档由程序在施工结束后补写；你在回复里如实写清做了什么、没做什么、卡在哪。

## 二、修问题时先过“三问”

修 bug 之前，先回答：
1. 问题出在哪一层？同类问题系统里还有没有别处？
2. 现在必须改，还是可以先不改？可以不改的，写明理由，不顺手改。
3. 修法和现有结构一致吗？不要为单个问题发明新机制。

修问题时，测试要先重现用户看到的问题：测试员交活时这条测试必须是不过的，开发员改好代码后才变成过。

## 三、别把项目越改越乱

后面接手的 AI 往往只看眼前的文件、照抄最近的写法；前一个 AI 留下的东西，后一个看不懂就会改乱。所以：

- 改之前先看清这次要改的东西还有谁在用；项目里已有现成做法的，照现有做法改，不另起一套。
- 看起来多余或奇怪的老代码，可能是前人为了防坑留的。没查清来历（用 git log 查是哪次改动加的、为什么）不许删；查不清就留着，在回复里写一句。
- 没帮上忙的改动要撤掉：一种改法没解决问题，先撤干净再试下一种，不要把“可能有用”的代码一层层叠上去。
- 新加的防护要有测试守着：只留一句注释提醒别删，后人照样会删。
- 代码里留提醒（临时、兼容、先这样），要写清为什么留、什么时候可以删。

## 四、记录放在哪里

- **总台账**（项目的 docs/开发进度跟踪.md）：按时间只追加，记每个关卡的结果，由程序补写。
- **卡片文件夹**（.collab/cards/卡片编号/）：需求、方案、执行记录（谁做了什么）、测试结果（每轮都保留）、返工记录、汇报。
- 只追加、不改写历史。发现记错了，追加一条更正，不删旧记录。

## 五、几条底线

- 测试员先写测试，开发员再写代码。
- 密钥、密码只放在 .env 或配置文件里，不写进任何记录或提示词。
- 推送、合并、发版，都由用户决定，AI 不擅自执行。
- 每次汇报：每条记录一小段，写清时间、耗时、最慢的一步、大白话解释、有没有报错；最后一句结论。推测要标明是推测。
- 只改任务卡片“允许改动的范围”里列出的文件。范围外的改动（包括临时脚本、草稿、汇报文件）会被程序直接撤销，白做。
- 不要提交（commit）、不要合并、不要推送；这些在用户点头后另行处理。

## 六、各角色要点

- **测试员**：只写测试，不改产品代码。测试要覆盖任务卡片里的每一条验收要点，并确认项目的测试命令真的会执行到你写的测试文件。测试只管结果对不对，不规定代码怎么写（比如不要求某段写在哪个函数里）；假的页面、假的工具要和真的行为一样，不要逼写代码的为迁就测试去改产品代码。复查退回后补测试：退回几件就补几条，逐条对应编号，不能漏。
- **开发员**：让测试全部通过；不要为了通过而修改或删除测试。只按施工单和任务卡做，没要求的功能、写法不要自己加。返工只改退回的那几件；要动旁边的写法，先确认原有的测试和说明都还在，不顺手统一或重写相邻的逻辑。项目里有现成的做法（比如跑测试、启动程序）就用现成的，不另写一套。完成后在回复的最后一行写“汇报：”加不超过 100 字的说明，由程序保存；不要另建汇报文件（项目目录里多出的文件会被判为越界）。
- **复查员**：只读，不改任何文件。第一行必须写“结论：通过”或“结论：不通过”，回复末尾附“复查清单：”加一个 json 代码块，每条问题写齐级别、来源、类型、碰上（常见 / 少见 / 极巧合）、现象、位置、证据（实跑写命令和输出，推演写对照的文件和行号）；退回后的复查按编号逐条回答上轮问题“改好了 / 没改好”。类型写功能问题、测试写错或安全或丢数据；只报在这个项目里碰得上的问题（实跑复现，或推演时指出本项目里会走到它的代码），碰上：常见＝正常使用容易遇到，少见＝本项目会发生、要特定操作（如停下后接着跑），极巧合＝恰好在两步之间被打断才出的、或本项目里根本没有会触发它的写法文件操作；只能推演的极巧合不退回、只记以后再修；只能推演的少见问题只有严重的才退回。只看这次改动是否符合需求和验收标准；台账、归档由程序在施工结束后补写，不算问题。
- **写方案的**：只读，不改文件。把任务卡变成程序能照着跑的开工单：一句话、步骤、不做什么、要问的问题、允许改哪些文件（尽量窄）、一条本卡测试命令（不安排跑全部测试）、怎么打开改好的版本（照项目里真实的入口写，不猜；查不到就空着）。卡片引用了施工单的，程序直接照施工单生成，读不全才轮到你，这时照施工单摘，不重新设计。
- **备交接资料的**：只读，不改文件。给写代码的整理“要改的地方现在怎么写、有哪些规矩要守”，写进交接资料，不写方案、不动手改。卡片引用了施工单的不用备（施工单就是交接资料）。
- **所有人**：会有看门人盯着动静（副本里的文件变化，或你的输出还在涨），连续 15 分钟都没有会被判定为卡住并停止；5、10 分钟没动静时行政会告诉用户。遇到需求看不懂、环境跑不起来，直接在输出里写清楚卡在哪，不要原地空转。
- **只跑本卡的测试**：派活时会写明本卡的测试命令，要确认就只跑这一条，不要跑全部测试（全部测试留到最后验收）。写测试的只改测试文件，改了原有的产品代码会被撤掉。
