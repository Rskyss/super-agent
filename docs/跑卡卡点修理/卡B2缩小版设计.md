> 2026-11-27，Claude 自己做（CARD-033）。依据《方案》“11-27 第三次修订”末节“B2′ 改用拿掉文件再跑一遍”、《任务清单》B2′ 行。
> 原 B2 和 B2′ 第一版（读测试工具结果）复查都实测出放过路径，用户选这个更笨但稳的做法：不读测试结果细节。

## 怎么判

全部测试没过、项目登记了还生效的已知没过名单时（dispatch.rerun_without_waiting）：
1. 名单读不懂 → 停下“名单读不懂”。
2. 名单里等卡的、副本里确实有的测试文件 → 在一份新副本里把它们拿掉（fullrun.remove_from_copy，只认副本里面的路径），**原样再跑一遍全部测试**（项目配的命令或 Python 逐文件跑都一样，带 `&&` 的也一样）。
3. 拿掉后全过、且不是 0 项 → 放行，流转写“名单里 N 个等卡的测试文件没过，拿掉后全部测试都过”。
4. 其余（拿掉后还有没过、跑不成、0 项、跑的时候代码变了、没登记）→ 照老规矩，用第一次的结果。

人工“接受剩下的问题”同样拿掉再跑，拿掉后全过就接受；名单读不懂就挡并写明。全部测试一次过就不多跑。

## 名单

`<项目>/.collab/已知没过.json`；`collab known-fail add <项目> --file 测试文件 --card 卡号 --why 原因`、`list`、`remove --file`。
- 只能登记整个文件（不能只登记几项）；只有“等卡”；路径只认项目里的相对路径。
- 读不懂、有写错的条目（含旧格式只登记几项的）→ 当名单坏了。
- 先记台账、再换名单：台账记不上就不换；换名单失败台账补一行“没成”。
- 卡放进项目时撤掉“等这张卡”的条目；等的卡已放进项目或放弃的条目自动不算。

## 代价和注意

- 全部测试没过、又登记了名单时，多跑一遍全部测试。
- 等卡的验收测试要单独放一个文件；别的测试引用了它（import），拿掉后会跑不起来，就照老规矩（不会放过）。

## 复查第 2 轮后改的（11-27）

- 名单只认一个测试文件（文件名像测试文件），不认目录、`__init__.py`、`conftest.py`、普通代码文件；副本里**真的拿掉了**名单里的每个文件才算（没复制进去、不是普通文件的都不算拿掉）。
- 第二遍要认得出**实际跑了几项**（unittest、node spec/tap、pytest 的汇总；跳过、待办不算），不是 0 项；报告格式给不出项数（如 node 的 dot）不放行。
- 第二遍用一份干净的缓存和临时目录（XDG_CACHE_HOME、TMPDIR、npm 缓存），不吃第一遍留下的缓存。
- 两遍之间施工副本的代码变了 → 不放行；第二遍跑完再读名单，文件不一样了（撤了、加了）→ 不放行；名单读不懂 → 停（全过时也停）。人工接受同样核对，写待验收前再读一次名单。
- 没登记过名单的项目不建锁、不碰 .collab。撤单先换名单再记台账（中途断了只会少一条豁免）。
- **已知限制（这个做法本身堵不住，写进《施工单怎么写》）**：等卡测试文件和老测试共用全局状态（例如关掉测试隔离后靠等卡文件加载的插件）；全部测试命令本身会看某个文件在不在而改变跑的范围。这两种情况拿掉文件后老测试的行为会跟着变。规矩：等卡的验收测试单独成文件、不被别的测试引用、不改全局状态；全部测试命令不按文件在不在变化。

## 复查第 3 轮后改的（11-27，用户定：修实际的，偏的记已知限制后放行）

- 数“实际跑了几项”：unittest 只认最后一段总汇总（不重复加）、跳过的不会算成负数；pytest 认简短汇总，只标了预期失败没跑正文的不算；第二遍只要实际跑的项数大于 0（不再另用“0 项”的老判断，组合命令前段跑过的会被算上）。
- 第一遍跑完到第二遍跑完之间代码变了 → 这组结果作废、停下说清（Python 项目不再拿第一遍的失败去和改之前比）。
- 人工接受：拿到状态锁、写“待验收”前再核对代码没变、名单没坏、名单还是这次拿掉的那几个文件。
- 名单路径中间经过目录快捷方式（符号链接）的不认。
- 没登记过名单的项目，放进项目、手动撤单都不建锁；名单锁文件只读时照样能读。撤单后台账没记上，命令行说清“豁免已撤、台账没记上”。
- **已知限制（这一轮新增，用户知情）**：两遍之间只改文件执行权限、等长改写还保留修改时间（施工副本按大小和修改时间认“变没变”）；测试命令里自己指定缓存目录、或写在 node_modules 里的缓存（第二遍隔离不了）。

## 复查第 4 轮后改的（11-27）

- 开跑时没有名单、跑的时候才第一次登记 → 这组结果作废、停下说清（自动关卡和人工接受都一样）。
- 认“跑了几项”：node 的 TAP 写了“一项都没有”（1..0）时认不清，不放行；项目自配的几段 unittest 命令各算各的再相加（程序自己逐文件跑的只认末尾总汇总）。
- 人工接受：拿到状态锁后，最后一次核对名单和写“待验收”都在名单的共享锁里做，撤单要等状态写完。
- 登记时路径中间有快捷方式（符号链接）的直接拒收。
- 撤单提示按实际结果说：名单已换好、台账没记上 → 说“已经撤掉了，台账没记上”；还没换名单就失败 → 说“没撤”。合并后自动撤单同理。

## 复查第 5 轮后改的（11-27）

- 开跑时没有名单就固定走老规矩，不进“拿掉文件再跑”；交结果时（第一遍过没过都一样）发现名单是跑的时候才出现的，这组结果作废。人工接受同样。
- 卡变“已合并”时和人工接受用同一把名单锁：接受核对名单、写“待验收”期间，等着的卡不会恰好变成已合并让豁免失效。
- 认“跑了几项”：node 只是“文件加载成功”的那一行（顶格、名字是文件路径）不算测试正文；TAP 一段写了“一项都没有”的这段算 0、别的段照算；程序自己逐文件跑还是项目自配命令由调用方明说，不靠输出里像不像分段标题来猜。
- 已知限制补一条：卡变“已放弃”时没有加这把锁（放弃和接受同时点的情况）。
