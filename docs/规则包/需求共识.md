# 需求共识：给大模型读的规则包（agents/）

> 2026-11-20 用户提出，状态：用户已批准（11-20“照这个顺序来，开始吧”）
> 大小判定：大需求（跨跑卡流程、行政、积木库管家多个模块，预计超半天）。走三份文档。
> 来由：CARD-019 复盘（docs/切换项目/复盘.md）。

## 用户原话（摘）

> 所有给大模型的规则不应该写在代码中间，应该有单独的一个文件包，把大模型需要读的分细，像 pstack 那样分了很多 md。
> 以后改规则就不用到代码里面改了。
> PM、架构师以后可以换成任何模型来做。现在是你（Claude）当，下次我换成其他大模型，它读了这个包就知道需求和施工单该怎么写、怎么提交给行政。
> 不要写在你的记忆里，一定是彼此交接，其他模型接入也能看到。

## 要什么（大白话）

1. 项目里有一个专门给大模型读的规则包，按“角色”和“手册”分成多份 md，有一份索引说明谁读哪几份。
2. 规则包是**唯一权威**：改规则只改包里的文件，不用改代码；程序给模型发话时，从包里读规则，只往里填卡号、文件名这类每次不同的内容。
3. **产品经理、架构师这两顶帽子可以换任何模型戴**：只读规则包，就能写出合格的需求共识、方案、任务清单、施工单，并知道怎么把“粘给行政的话”交给用户。不依赖 Claude 的记忆，也不依赖之前的聊天。
4. 把 CARD-019 复盘出来的几条写进包里：
   - 施工单怎么写：必备几节、**状态表**（记住状态/切回恢复/共用数据的功能必填）、**原有行为清单**、测试怎么写、交出前自查；附模板。
   - 写代码的：修退回的问题如果要改原有行为，停下不改，写进汇报。
   - 复查员：对着施工单的原有行为清单看，清单里的行为被改了标严重；“极巧合”的具体意思（加载、切换一两秒空档里才出的）。
   - 写测试的：页面行为用实跑页面的检查，逐字比对代码只用于跑不起来的窗口外壳。
   - 接手卡片：接手的人交用户点“接受”前，先在副本里把全部测试跑通。

## 已查到的现状

- 现在给模型的规则分散在三处：一份规则文件 `collab/规则.md`（54 行，各角色一段）；跑卡流程代码里约 300 处拼出来的话；行政、积木库管家的提示词在另外的代码和 `desktop/clerk/roles/` 里。
- 开发流程规范（docs/开发流程规范/开发流程规范.md）是写给 Claude 当产品经理/架构师用的，里面混着给用户看的摘要和给模型看的细则。
- Claude 的记忆里也有不少流程规矩（如“备卡和接手的教训”“同一角第二轮就砍”），其他模型看不到。

## 不做

- 不改跑卡流程本身（谁先谁后、退回几次这些程序判断不动；2b 待定）。
- 不改超级玩家。
- 第①步只搬和 1～5 条有关的几处，其余提示词留到第③步。

## 怎么算验收通过

1. `agents/` 里有索引、通用、角色、手册几类，索引写清每个角色读哪几份。
2. 换一个没参与过的模型（如 Codex 或 Gemini），只给它规则包和一句需求，它写出的需求共识、施工单符合包里的要求（含状态表、原有行为清单、粘给行政的话）。由 Claude 和用户对照检查。
3. 跑卡时各角色读到的是包里的规则（第一期：原来读规则文件的地方改读包，跑一张小卡确认）。
4. 第二期每搬完一个角色，那个角色在一张真实卡上干活效果不变，相关测试全过。
5. Claude 记忆里的流程规矩，凡是其他模型也该遵守的，都已搬进包；记忆里只留指向包的一行。

## 泼冷水

- **第二期是大活**：跑卡流程代码里约 300 处话，很多老测试是直接对着这些话检查的，搬走后要跟着改测试，必须一个角色一张卡慢慢搬。
- **“换个模型照样写得好”只能尽量**：规则写得再细，便宜模型也可能漏；验收第 2 条就是专门检验这件事的，第一次多半要回来补规则。
- **小修三条要等第一期做完**：用新规则写小修施工单，正好检验规则包。小修会晚一点开工。
