第 2 次发现的两处小毛病：

1. **验收命令写成 `python3 -m unittest tests.xxx`，本机跑不起来**（装着一个同名的 tests 包，挡住了项目的测试目录）。根子在规则包：README 里唯一的例子就是这种写法。已改 README 例子，并在《施工单怎么写》写明一律用 `discover -s tests -p` 写法。
2. 拍板口径表里“发给行政什么”标的是“我替用户定”，但第一条回复已经把它当问题问了，前后标法不一致。影响小，没补规则。

**Claude 初判“合格”，被 Codex 复查推翻，已更正：第 2 次不算合格。** Claude 只核对了“引用的代码在不在”，没有逐条核对施工单能不能直接派工。Codex 查出 4 条中等问题，Claude 逐条核实都成立：

1. 漏查跟新口径冲突的老测试：`test_rightfix_acceptance.py` 要求标题下收起时只显示一行，`test_flowfix_b_extra_history.py` 要求没有实时输出时显示派活说明，两处都会和新做法打架，原稿没列；原有行为“可展开看完整内容”对应的测试也写错了文件。
2. 行政模型失败时显示什么、要不要重试，前后写法矛盾（一处写显示固定短句，另一处写显示旧摘要）。
3. 原稿承诺“展开还能看原文”，但它规定的做法把原文换成了摘要，又不许改页面脚本，按施工单做出来展开后看不到原文。
4. 摘要的检查条件漏了“不显示代码、命令、文件路径”，这是《产品经理》里已有的口径。

另有轻微 2 条：查同类产品时没写用户反馈；两处行号差几行。

**判断**：这 4 条在规则包里都**已有规矩**（全仓搜冲突老测试、不留给施工方猜、进度说明不显示路径），不是缺规则，是 GLM-5.3 没照规则做到位。现在的流程里，施工单写完直接派工，到施工完的复查才会发现，届时要多退回几轮。是否在“施工单派工前”加一道独立复查，会改变已批准的流程，停下等用户定。

**用户 11-20 定**（原话“需要交 Codex 复杂的”）：中、大需求的施工单开工前先交 Codex 极高档复查，通过了才给粘贴的话；小需求不用。写进《施工单怎么写》第八节，判大小、复查和验收、README 要点表各加指向。Codex 复查第 1 轮中等 3 条（第 3 轮后的出口套用了施工后的规矩、拆几张施工单时轮数怎么算、开工前看什么测试证据），都核实修好，确认复查通过。
