# 方案：开发流程规范

> 依据 [需求共识](需求共识.md)（用户 2026-11-17 批准）。**本方案用户 2026-11-17 批准（“批准，写任务清单”）。**
> 本方案只讲“规范长什么样、怎么写、怎么验”，并把规范里最关键的几张表**直接写在这里**让你审；批准后《任务清单》再拆活，正文照本方案写。

## 1. 成品长什么样

一份文档：`~/Desktop/project/开发助手/docs/开发流程规范/开发流程规范.md`。

- **开头一页纸摘要**：新会话的 Claude 只读这一页就能开工——谁戴什么帽、流程九步、哪些情形必须停下问你。
- **后面是细则，共 12 节**（和共识第 3 节一一对应），每节都能回答“这条拦住过什么问题”，答不上来的不写。
- **末尾三样**：规矩来源对照表、“待你决定”、使用记录（见第 7 节）。
- **模板放在同一份文档的附录里**（影响面清单、范围变更登记），不另开文件，避免散。
- **让以后的会话读到它**：批准后我在记忆里加一条指针（位置 + “开发前先读一页纸摘要”）。**不改你的全局规则文件。**

和 vibe-workflow 的关系：规范**只写增量和映射**，不复制它的细则。

| vibe-workflow 里的 | 规范里对应的 |
|---|---|
| 关卡①对齐（大需求走 6A，三份文档） | PM 关 |
| 关卡①·修问题分支的“架构关三问” | 架构关（**扩大到所有中、大需求**，并加影响面清单） |
| 关卡②施工、关卡③没全绿不报完、关卡④台账 | 施工、最终验收、收尾（原样引用） |
| 借口对照表、红旗清单 | 原样引用，不重写 |

## 2. 角色和帽子（现状，不改分工）

| 谁 | 戴什么帽 | 管什么 | 不管什么 |
|---|---|---|---|
| **你** | 决策人 | 提需求、点头批准、真实窗口看一眼、验收；影响体验/花钱/方向的拍板 | 看代码、写文档 |
| **Claude** | **PM 帽 + 架构师帽 + 最终验收人** | 判大小、写《需求共识》《方案》《任务清单》、核实复查意见、最终验收、台账 | 自己改的代码自己复查；替你拍板 |
| **行政** | 前台 | 和你聊清需求、出确认框建卡、答进度 | 写方案、改代码 |
| **写方案**（Codex 低档） | 转抄 | 读施工单，摘出做什么、能改哪些文件、验收命令 | 重新设计 |
| **写测试**（Codex）、**写代码**（千问/Cursor/agy，正在对比）、**复查**（Codex 极高档，换人） | 施工队 | 按单施工；写代码的不许改测试 | 超出方案的改动 |
| **程序** | 裁判 | 判过没过、拦越界改动、盯卡住 | — |

**帽子是怎么对应关卡的**：PM 帽 → 《需求共识》（要什么、不做什么、怎么算做好）；架构师帽 → 《方案》（怎么做、会牵连到什么）。两顶帽子都由 Claude 戴，**不增加任何新的 AI**。

## 3. 流程和关卡（规范的核心表）

| # | 关卡 | 谁做 | 出什么 | 你点头？ | 必须停下来问你的情形 |
|---|---|---|---|---|---|
| 0 | 判大小 | Claude | 一句话：“这是小/中/大，因为……”（沿用 vibe-workflow 五条标准） | 否 | 拿不准 |
| 1 | **PM 关·对齐** | Claude（或行政）与你 | 大需求：《需求共识》；小需求：选择题 + 台账一行 | 大需求要 | 影响体验、花钱、方向的歧义 |
| 2 | **架构关·方案** | Claude（带施工单的卡：“写方案”那步转抄） | 《方案》：做法 + **影响面清单** + 泼冷水 | 要 | 发现和已批准文档矛盾；影响面超出共识范围 |
| 3 | 拆任务 | Claude | 《任务清单》：每项“做什么、怎么验收、依赖谁” | 大需求要 | — |
| 4 | 施工 | 开发助手，或 Claude 亲自（分工规矩沿用你 11-14 的授权） | 先写会失败的测试，再写代码；一次只让一个人动手 | 否 | 要改的超出已批方案（→ 记入“施工中补充”，待你确认，**不顺手改**）；同一问题连败两次换办法、三次上报 |
| 5 | 复查 | Codex 极高档（换人） | 复查报告（严重/中等/轻微） | 否 | 3 轮到顶仍有中等问题 |
| 6 | 最终验收 | Claude | 全量测试 + 真实窗口走查 + **逐条核实**复查意见 | 否 | 走查需要真实点击（→ 请你点一次，不发模拟点击） |
| 7 | 收尾 | Claude | 台账、文档同步、关卡清单（测试 / 真实走查 / 独立复查 / 台账 / 文档同步，没做的写“未做”） | 否 | — |
| 8 | 交付 | 你 | 验收；提交、推送、发版**先问你** | 要 | 一切对外动作 |

**除了上面的“必须停下问你”，其余 Claude 自己定并记录**：技术做法、测试写法、模型和工具选择（在你已授权的范围内）。

**文档怎么交到开发助手手里：你复制粘贴，不开发新角色**（用户 11-17 确认）。Claude 写文档（《需求共识》《方案》《施工单》），你把它复制进对话交给行政建卡。为了粘贴不丢信息，凡是交给开发助手的活，Claude 在施工单末尾附一段**可直接粘贴的话**：施工单路径、要做什么、不做什么、怎么算做完、允许改哪些文件、验收用哪条命令。这是现在已有的做法（施工单 README 末尾的“发给行政的话”），这次写成规矩。

## 4. 架构师帽的三条原则 + 影响面清单

**三条原则**（都来自这次的教训）：
1. **规则放在所有入口的必经处。** 不要在某一个入口各拦一次。（这次“行政必配”先放在团队页里，结果左栏“新对话”、菜单都绕得过去；改到外壳一处才对。）
2. **和现有做法同构。** 优先复用已有机制，不为一个问题发明新办法（沿用 vibe-workflow 架构关三问）。
3. **“不受影响”必须附证据。** 方案里写“某某不受影响”，要写搜索关键词和结果；写不出就改成“我不确定”。（这次我先说“超级玩家那套不受影响”，后来证明开发助手里那份副本受影响。）

**影响面清单**（中、大需求在《方案》里必填；小需求只做第 2 问里的一条搜索）：

| 问 | 要写什么 |
|---|---|
| 1. 动的是什么？ | 名字和关键词，全仓搜（代码、测试、页面文字、外壳、配置、文档、记忆）出现在几个文件 |
| 2. 谁在读它、谁在写它？ | 逐处一句话：要跟着改 / 不用改 + 理由 + 搜索证据 |
| 3. 有几个入口？ | 用户从哪几条路能走到：菜单、按钮、快捷键、链接、命令行、自动流程；规则放在必经处了吗 |
| 4. 会连带变什么？ | 文档、测试、界面文字、台账、README、记忆 |
| 5. 和已批准的文档矛盾吗？ | 对一遍共识、方案、台账口径；矛盾就**先改文档、再动手** |
| 6. 老数据、老配置、已装的应用怎么办？ | 兼容怎么做；要不要重装、迁移；会不会影响正在跑的卡 |
| 7. 这次明确不改什么？ | 写清楚，施工中碰到就走“范围变更” |
| 8. 怎么证明做对了？ | 哪条测试、哪次走查 |

## 5. 其余几条规矩（来自你已定的，原样收进来，标出处）

- **谁不能验谁**：写的人不自己验收；Claude 写的代码交 Codex 复查；复查人换家；复查指出的问题 Claude **逐条核实再改**（对方论据错，不等于它的怀疑没价值）；复查最多 3 轮，到顶由 Claude 最终验收并如实记遗留。（出处：记忆“Codex 复查循环”、vibe-workflow）
- **测试不许为了变绿而弱化**（**新增**，这次的教训：我把 6 个测试跳过、另 2 处断言改成接受退化）：改老测试只改“因需求变化而必变”的断言，逐条登记原因；**跳过测试要你点头**。
- **范围变更**（**新增**）：施工中发现要改的超出已批方案，先停下，登记到《任务清单》末尾“施工中补充”（改了什么、为什么、怎么撤），标“待你确认”。只有不改变任何行为的文字、注释同步可以顺手做，也要登记。
- **测试节奏**：修改轮只跑相关；代码定稿后才开全量；改外壳只跑读外壳源码的那批；收尾一次全量，分组并行跑。（出处：记忆“测试节奏”“交接零等待”）
- **真实窗口走查守则**（**新增**）：用应用自带的自测开关，不碰真钥匙串；只截应用自己的窗口；**不发真实鼠标点击**——这次窗口被移到了另一块屏幕，点击可能落在别的程序上；要点击就请你点一次。（出处：这次教训，已记进记忆）
- **汇报**：产品语言、事实和推测分开标；说“做完了”之前列关卡清单。（出处：你的全局规则、记忆“汇报写法”）
- **分工**：沿用你 11-14 授权——有施工单的交开发助手；挡路的、很小的、做实验、把关、危险的、改外壳后重装，Claude 亲自做。
- **交接靠复制粘贴**：Claude 写文档、附可直接粘贴的话，你粘给行政；不为“PM”“架构师”开发任何角色或功能。

## 6. 倒推检验：拿“去掉调度员”这次验证规范有没有用

这一张表是验收标准第 4 条，写进规范附录当例子：

| 这次实际发生的问题 | 实际怎么发现的 | 新规范下会在哪个关卡被拦住 | 靠哪一条 |
|---|---|---|---|
| 开发助手里超级玩家那份“接调度员”检测读不到调度员，我却把它的 6 个测试跳过了 | Codex 复查第 1 轮 | **架构关**：第 2 问搜 `调度员/dispatcher` 就会列出这几处；**复查关**：跳过测试要你点头 | 影响面清单第 2 问；“测试不许弱化” |
| 我的方案前后矛盾（一处写“没配行政就停在团队页”，一处写“老项目仍走旧聊天”） | Codex 复查第 1 轮 | **架构关**自查 | 影响面清单第 5 问 |
| “行政必配”只放在团队页，左栏“新对话”、菜单都绕得过去 | Codex 复查第 2 轮 | **架构关** | 原则 1（必经处）+ 第 3 问（入口） |
| 超出方案的顺手改（行政那句话、停用确认框、占位文字，还有“顺手清理老字段”） | 我自己动手时发现，后来 Codex 又指出一处 | **施工关**：先停下登记、标待确认 | 范围变更规矩 |
| 我说“超级玩家那套不受影响”，后来证明不对 | Codex 复查第 1 轮 | **架构关**：不受影响要附搜索证据 | 原则 3 |
| 真实窗口里发了模拟点击，窗口已被移走，可能点到别处 | 我自己发现 | **最终验收关**：走查守则 | 走查守则 |

**诚实地说**：这是事后倒推，只有一个案例，样本很小；表里“会被拦住”是我的判断，不是实测。

## 7. 怎么知道它有没有用（防走过场）

规范末尾有一节**使用记录**，之后每个真实任务填三行：哪个关卡拦住了什么、哪条是走过场、哪条嫌慢。

**复盘规则**：跑满 3 个真实任务后复盘一次——
- 没拦住过东西的条文，删。
- 如果这 3 个任务里**至少 2 次**还是被 Codex 复查抓出“影响面遗漏”，说明光靠清单不够，再考虑你之前没选的那个折中：在批准方案之前加一道**一次性、只读、有清单**的方案评审（不是常驻角色，不写代码）。
- 影响面清单要不要做进开发助手（比如“写方案”多一节、超范围改动自动停下），也在复盘时定。

## 8. 怎么验这份规范本身

1. **对账**：每条规矩标出处；逐条对一遍你的全局规则、vibe-workflow、记忆里的分工和复查规矩，**有冲突的不自己改，列进“待你决定”**。
2. **倒推表**：第 6 节那张，全部能对上。
3. **Codex 独立复查文档**（只读，极高档）：找遗漏、互相打架、含糊的地方，我逐条核实再改，最多 3 轮。
4. **你批准**。

## 9. 泼冷水

- **规范靠自觉，不是程序强制。** 台账和关卡清单有 hook 硬拦，影响面清单没有。所以才有第 7 节的“使用记录 + 3 个任务后复盘”。
- **证据很薄。** 见第 6 节末尾。
- **太长没人读。** 一页纸摘要打头；细则可查；每条都要能回答“拦住过什么”。
- **规矩多了会拖慢。** 小需求走轻量路径：对齐 → 做 → 测 → 台账，加一条“谁在用它”的搜索，不要影响面清单全套。
- **Claude 自己也会违反。** 所以规范里的“必须停下问你”写成明确的触发清单，不靠判断。
- **你的全局规则里 6A 的文件名**（ALIGNMENT_ 等）和 vibe-workflow 的（需求共识 / 方案 / 任务清单）不一致，你已经写明“以 vibe-workflow 为准”，规范沿用，不动。

## 10. 工作量和不改什么

- **工作量**：写正文约 1–2 小时，Codex 复查 1–2 轮；这是估计。
- **不改**：任何工具代码、你的全局规则文件、vibe-workflow 技能本体、超级玩家的任何东西。
- **会新增**：这份规范、记忆里一条指针、台账登记。
