# 需求共识：开发流程规范

> 2026-11-17 · 用户说“你帮我规范好开发流程，这个很重要”，并转述一位开发的建议：“还可以搞个 PM 和架构师，进行工程化研发，有大局观又有注意力”。Claude 给了判断和两个问题，用户答“都按推荐”。本文是对齐结果，**用户 2026-11-17 已批准**（“批准，写方案”）。

## 1. 要做什么

写**一份**《开发流程规范》，成为“你、Claude、开发助手”这三方做开发时的唯一依据。

它要解决的不是“缺人手”，而是**规矩散在各处**：你的全局规则（6A、vibe-workflow）、十几条记忆里的分工和复查规矩、台账里的口径。每次新会话都要重新拼，拼漏了就出事。这次“去掉调度员”就是例子：Codex 复查三轮，抓出来的主要问题都是**影响面遗漏**、**文档前后矛盾**、**范围外顺手改**，这些本该在开工前就被拦住。

## 2. 你定下的两件事（口径）

| 问题 | 你的选择 | 含义 |
|---|---|---|
| 范围 | **A**：只规范“你 + Claude + 开发助手”这套流程，工具本身不改 | 本次只出文档；工具改动（比如“写方案多一节影响面”“带施工单的卡直接开工”）以后另提 |
| PM 和架构师的形式 | **A**：用“帽子 + 关卡”，不加新的 AI 角色 | PM、架构师是**现有的人戴的帽子**，各自对应一个关卡和一份文档 |

**为什么不加新 AI 角色**：你 11-07 的《多模型协作调研》结论——模拟一家软件公司（PM、架构师、开发、测试一起上）的做法，在大规模研究里失败率 41%–87%，ChatDev 只有 33% 做对；每多一个角色就多一次交接，丢一点信息，也多花额度。有用的只有三种：一个人动手、复查换人并真跑测试、方案由强模型来写。

## 3. 规范里要写什么（大白话）

1. **角色和帽子**
   - 你：提需求、点头批准、在真实窗口看一眼。
   - Claude：PM 帽 + 架构师帽 + 最终验收人。
   - 行政：前台，聊清需求、建卡。
   - 写方案（Codex，低档）、写测试（Codex）、写代码（千问/Cursor/agy，正在对比）、复查（Codex 极高档，换人）。
   - 程序：判过没过、拦越界改动、盯卡住。
   - 这一节只描述**现状**，不改分工。
2. **流程和关卡**：需求 → **PM 关**（《需求共识》：要什么、不做什么、怎么算做好）→ **架构关**（《方案》，含**影响面清单**）→ 你批准 → 《任务清单》→ 施工（一次只让一个人动手）→ 复查（换人、真跑测试、最多 3 轮）→ Claude 最终验收 → 记台账、同步文档 → 你验收 →（提交、推送先问你）。
3. **每个关卡写明四件事**：谁做、出什么文档、你要不要点头、什么情况下必须停下来问你。
4. **按大小走不同的路**：沿用 vibe-workflow 的五条判大小标准；小活走轻量路径（对齐选择题后直接做，仍要测试和台账）；**这次不做“快速档/完整档”**，只在规范里留一个位置。
5. **什么活交开发助手、什么活 Claude 亲自做**：沿用你 11-14 授权的规矩（有施工单的交开发助手；挡路的、很小的、做实验、把关、危险的、改外壳后重装，Claude 亲自做）。
6. **影响面清单**（新增，规范里最重要的一块）：中、大需求在《方案》里必填——谁在读/写这个东西（全仓搜）、会连带变的文档/测试/界面文字、和已批准文档是否矛盾、老数据和老配置怎么兼容、要不要重装或迁移。小需求只做“谁在用它”这一条。附一个可直接照抄的模板和一个真实例子。
7. **范围变更规矩**：施工中发现要改的超出已批方案，**先停下、记进“施工中补充”并标待确认，不顺手改**；只有不改变任何行为的文字、注释同步可以顺手做，但要登记。
8. **谁不能验谁**：写的人不自己验收；Claude 写的代码交 Codex 复查；复查人换家；复查指出的问题 Claude **逐条核实再改**（对方论据错，不等于它的怀疑没价值）；复查最多 3 轮，到上限由 Claude 最终验收并如实记遗留。
9. **测试节奏**：沿用已定的节奏（修改轮只跑相关，代码定稿后才全量，改外壳只跑读外壳源码的那批，收尾一次全量），并写明本次学到的“分组并行跑全量、别在代码没定稿时开跑”。
10. **关卡清单和汇报**：说“做完了”之前列“测试、真实环境走查、独立复查、台账、文档同步”，没做的写“未做”；汇报用产品语言，事实和推测分开标。
11. **真实窗口走查守则**：用应用自带的自测开关；只截应用自己的窗口；**不发真实鼠标点击**（本次窗口被移走，点击可能落到别处）；需要点击就请你点一次。
12. **规矩来源对照表**：每一条规矩标明出处（你的全局规则 / vibe-workflow / 哪条记忆 / 本次教训），方便以后改、也方便对账有没有冲突。

## 4. 明确不做

- 不加新的常驻 AI 角色（PM、架构师不是新 AI）。
- 不改开发助手和超级玩家的任何代码。
- 不改你的全局规则文件（`~/.claude/CLAUDE.md`）和 vibe-workflow 技能本体：规范**引用**它们，不复制、不替换。发现冲突，记在规范末尾“待你决定”。
- 不做“快速档/完整档”分档（只留位置）。
- 不规范超级玩家产品里给普通人用的“业务流程”（你选了范围 A，那是另一件事）。

## 5. 验收标准

1. 《开发流程规范》放在固定位置，**开头有一页纸摘要**，后面是可查的细则，全文用产品语言。
2. 每个关卡都写明：谁做、出什么文档、你要不要点头、什么时候停下问你。
3. 和已有规矩**逐条对账**：附“规矩来源对照表”，没有互相打架的条文；有冲突的列在“待你决定”。
4. **拿真实任务倒推检验**：用“去掉调度员”这次，列出“如果当时有这套规范，哪几个问题会在哪个关卡被拦住”，至少对上 Codex 复查抓到的那几类（影响面遗漏、文档前后矛盾、范围外顺手改、自己验自己）。
5. 影响面清单有可直接照抄的模板，并带一个真实例子。
6. Codex 独立复查这份文档（只读）：找遗漏、冲突、含糊处，我逐条核实后改；最多 3 轮。
7. 你批准后：在记忆里加一条指针（以后新会话先读规范），台账登记。

## 7. 泼冷水（风险和我不确定的）

- **规范靠自觉，不是程序强制。** 现在的台账和关卡清单有 hook 在硬拦；但“影响面清单”没有强制机制，可能变成走过场。建议先按规范跑 2–3 个真实任务，看有没有用，再决定要不要把它做进工具。
- **证据很薄。** “影响面清单能提前拦住大部分问题”只是用这一次任务倒推，只有一个案例，是推断，不是量出来的。
- **太长没人读。** 所以要求一页纸摘要打头，细则可查。
- **和 vibe-workflow 重复。** 所以只写增量和映射，引用不复制。
- **规矩多了会拖慢。** 小活必须有轻量路径；规范里每条都要能回答“这条拦住过什么问题”，答不上来的不写。
