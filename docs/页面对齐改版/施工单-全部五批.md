## 〇、这次和以前最大的不同（必读）

用户 11-16 退回了前三批的界面：**“现在跟对齐完全不搭，我根本没有办法接受。”** 原因是以前复查把“沿用 DSH 原样布局”也算过了。用户定的总原则：

- **DSH 只当底层**（对话、调模型、存 Key、插件、跑工具）。
- **大布局按我们的设计图**：每页怎么排、分几块、文字和按钮在哪，全按图。
- **交互框架、图标、字体、颜色、按钮这些基础零件用 DSH 的**（`@deepseek-ai/dsh-client-ui-primitives` 的 Button 等、`--dsw-*` 颜色变量、DSH 图标）。不自己另画按钮和配色。

  - DSH 里能直接用的（服务、零件、现成功能）就用，不重写。
  - 暂时不用的 **一律不删代码**：DSH 的界面插件在 `dsh-plugin/core/cordis.patch.yml` 里加 `disabled: true` 关掉（每条上面一行中文注释写“藏的是什么、放回来删掉这条即可”）；我们自己插件里被换下来的部分（比如原来挂在 DSH 左栏里的注册），**把注册那几行注释掉并写明原因**，组件代码留着。
  - 每一处都登记进已藏清单，以后开放时照清单一项项放回来。

所以本批的**验收标准就是设计图**：`docs/借鉴DSH/页面对齐/` 里的 png（`mockup.html` 是源文件，可以打开量尺寸、取文字）。图上写“超级助手”的读作“超级玩家”。**图上没有的东西露出来 = 不通过。** 不许拿“DSH 原来就这样”当理由；真要偏离图，停下写进台账问 Claude。

### 〇之二、设计图是草图：结构按图，样子按 DSH 规范（用户 11-16 补充，以此为准）

用户原话：“我的设计图是一个草图，可以规范地设计；一定要参考我这种设计的方式，让它变得设计更规范。可以用 DSH 那边的交互框架、底层框架。”

| 必须和草图一致（验收逐项对） | 按 DSH 规范做、不用抠草图 |
|---|---|
| 页面分几块、每块在哪（左栏 / 中间 / 右栏，卡贴在输入框上面…） | 具体尺寸、间距、行高、对齐 |
| 每块里有什么、顺序是什么（品牌 → 新会话 → 对话/任务 → 列表 → 设置） | 字体、字号、字重 |
| 文字和叫法（标题、按钮名、提示语、分组名） | 颜色、深浅色、圆角、阴影、边框 |
| 按钮有哪几个、各做什么；状态怎么表示（橙点 = 等你、转圈 = 真在跑…） | 按钮、输入框、标签、表格、弹框、菜单这些零件的样子（用 DSH 现成零件） |
| 流程怎么走（一步一步展开、确认才建卡…） | 图标（用 DSH 的图标库）、悬停、动画、焦点、键盘操作 |
| 图上没有的不露出来 | 草图没画到的细节：照 DSH 同类地方的做法 |

- 草图里画得粗糙、不统一的地方（按钮大小不一、间距随手、颜色随手），**一律按 DSH 规范统一**，不要照着粗糙的样子抄。
- 但**不能借“规范”改结构**：比如不能因为 DSH 习惯把模型选择放输入框下面，就把它放回来；不能把左栏的“对话 / 任务”换成 DSH 原来的列表样式。
- 并排对照图的看法：先看结构、内容、文字、按钮、状态是否和草图一致（不一致 = 不通过）；再看是不是统一用了 DSH 的规范样子（自己乱画的按钮、配色 = 不通过）。
