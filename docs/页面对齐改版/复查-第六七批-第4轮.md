结论：不通过

1. 【中等】大项目即使没有新增改动，每一步“看改动”也会重复核对大量文件，开始干活和交活都变慢。原来的漏记已修好，但把索引副本时间拨早 24 小时带出了明显的性能回归。

   用户看到的现象：项目刚拉下来、刚切过分支，或最近一天更新过大量已跟踪文件时，写测试、开发、返工每一步前后都会重新读这些文件。文件已经暂存且没有再次变化，下一步仍会重复付出这个开销。独立临时仓库中，512 MiB 未改动文件的单次快照从约 0.056 秒变成约 1.025 秒，约 **18 倍**；一步前后两次快照合计约 2.05 秒，对照约 0.11 秒。

   原因和位置：`collab/dispatch.py:719` 至 `:725` 每次复制真实索引后，都把副本时间设为当前时间减 24 小时。它使近 24 小时的文件反复进入内容复核，不能继续利用原索引的未变化判断。每次快照都重新复制并拨时间，上一次复核的结果不会被下一次复用。`:763` 和 `:793` 分别在步骤前后调用快照。`:712` 的 5 MiB 过滤只保护未跟踪文件，也不能限制这部分已跟踪文件的开销。

   实测复现方法（全部在临时目录，不修改工作区源码）：

   - 初始化 Git 仓库，生成 128 个 4 MiB 普通二进制文件，总计 512 MiB；把它们的 mtime 设为一小时前，`git add -A` 后提交。此后不再改动文件。
   - 交替调用真实 `_tree_snapshot`，各测三次。对照组仅在测试进程内用 `mock.patch.object(dispatch.os, "utime", return_value=None)` 禁用拨时间这一个动作；其余快照实现和 Git 命令完全相同。对照文件时间早于真实索引，避开同秒碰撞，适合比较正常的未改动快速路径。
   - 六次返回的树编号全部相同，均未超时；真实索引字节、索引 mtime、暂存 diff 和 HEAD 在测试前后也全部相同。

   ```text
   Git：2.54.0 (Apple Git-157)
   对照，未拨早时间：0.0562 / 0.0558 / 0.0562 秒
   当前，拨早 24 小时：1.0262 / 1.0210 / 1.0278 秒
   中位数之比：18.26
   ```

   这是合成大仓库的本机测量，不代表用户项目已有同样延迟；没有实测到 60 秒超时，也没有把更大规模的耗时外推当成复现结果。但本轮要求核对“大仓库开销有没有明显放大”，上述对照已确认放大，且连续快照不能摊薄这项成本。需要收窄强制复核范围，同时保留同秒同大小修改的正确性验证。新增 `StepDiffRacyTest` 验证能看到修改，未覆盖未改动大仓库的重复扫描开销。

**并发重演结果**

初始标准均为“标题黑色、单击保存”。先通过真实运行中 `apply_revise` 确认“标题改蓝色”，收到排队提示；随后撤掉旧运行记录，把卡设为待验收，同时触发自动生效和基线仍为原两条的“改双击保存”。用线程事件暂停真实需求卡原子写回之前，确保另一入口确实到达锁并等待。只替换副本同步和启动子进程；启动替身写入真实存活运行记录，不启动施工程序。写回和锁只包同步观测层，仍调用原实现。

| `decide`，自动先完成 | 蓝色要求保留；第二条抛出“验收标准已发生变化，请刷新后再试”；提议仍为 `open`，没有被误标成确认成功。 |
