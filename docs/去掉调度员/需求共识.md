# 需求共识：开发助手去掉“调度员”这一行

> 2026-11-17 · 用户问“轻量级开发助手还需要调度员吗”→ 讨论后用户说“开始”。本文是对齐结果，**待用户批准**（连同方案、任务清单）。
> 适用：开发助手（`~/Desktop/project/开发助手`，dev-assistant 线）。超级玩家不动。

## 1. 为什么做

开发助手里，你的做法是 Claude 先写好施工单，再交进来建卡。调度员在这里只剩两件后台活，而且你从不和它对话：

1. **写方案卡**：读施工单，摘成“做什么、哪些文件能改、用哪条命令验收”。已有施工单时它不再设计，只是转抄。
2. **开工前备交接资料**：和写测试同时进行，告诉写代码的人“改哪里、现在怎么写”。备不成不挡流程。

可它在团队页占一整行，是**必配项**（不选就不算配好，第一次还得测通才能保存），用的又是 Codex 的额度。轻量化的方向下，这一行是多余的座位；两件后台活本身还有用，要保留。

## 2. 要做成什么样（用户能看到的）

| # | 变化 |
|---|---|
| 1 | 团队页只剩四行：**行政、写测试、写代码、复查**。没有“调度员”，也没有“自定义调度员命令”那个输入框 |
| 2 | 第一次使用的门槛保持现状，只是少了调度员这一项：团队要保存，三位执行员必须全部测通；行政配好后可以先不管团队、直接回对话（现在就是这样，改动没存时会提示，不悄悄丢） |
| 3 | 已经配过的老项目：配置里残留的“调度员”选择悄悄忽略，不报错，不影响“已配置”状态 |
| 4 | 写方案、备交接资料照常工作：**固定用 Codex，思考强度固定“低”**（和你现在给调度员设的一样）。模型跟“写测试”那位用同一个；写测试不是 Codex 时用 Codex 的默认模型 |
| 5 | 右栏流程里原来叫“调度”的那一站，改叫“写方案”，显示 `Codex · 模型（低）` 和用时 |
| 6 | 窗口标题不再写“调度员：xxx / 还没选调度员”，只写项目名 |
| 7 | 行政成为必配：左边聊天只和行政聊（没配行政时，原来“退回去和调度员聊”的路没有了，会先停在团队页） |
| 8 | 不是 git 的文件夹：团队页只显示行政一行，不出现“调度员”字样，也不崩 |

## 3. 明确不做

- **不删**“和调度员聊天”的旧通道代码（Codex 聊天那套）和外壳里的相关代码：只是不再有入口，清理另议。
- **不改**“需要调度员看看 / 等调度员最终核验”这类提示文案。这些话里的“调度员”指的是负责推进的人（你或 Claude），改措辞要动二十多处文字和几十条测试断言，另议，不在这次。
- **不动超级玩家**，也不动 `dsh-plugin` 和 DSH 那套“接调度员”接口：它们是超级玩家产品用的，开发助手里本来就没有入口。为了让开发助手仓库里还留着的那份副本照样能用、测试不跳过，配置层只留了一对读写老调度员的出口（`legacy_dispatcher` / `save_legacy_dispatcher`），团队本身看不到它。
- **不改施工流程**本身（写测试 → 写代码 → 跑测试 → 复查 → 你验收）。
- **不改协作包命令行**（Claude 在终端里当调度员用 `collab`）。

## 4. 验收标准

1. 团队页是四行，页面里找不到“调度员”三个字（含输入框、提示语）。
2. **全新项目**（没配过团队，行政也没配）：打开先出团队页；三位执行员有一项没测通就不能保存团队，全通才能保存；行政配好后可以不存团队直接回对话，团队有改动没存时会提示。这两条和现在的行为一致，只是不再有调度员那一项。
3. **老项目**（配置里带 `dispatcher`）：打开不报错，团队页显示“已配置”。
4. 建一张有施工单的卡：写方案成功，记录里写方案用的是 Codex、强度“低”；交接资料照常生成。
5. 右栏出现“写方案”这一站，带模型和用时；7 站顺序、转圈、打勾都和以前一样。
6. 非 git 文件夹：团队页只有行政一行，保存、返回对话正常。
7. 全部测试通过。因“去掉调度员”而必须变的老测试，逐条在验收记录里写明改了什么、为什么；不删测试。
8. Codex 复查通过（最多 3 轮）。
9. 真实窗口、干净环境走查：新项目、老项目、非 git 文件夹三种，各截图。

## 5. 我替你定的（可以改）

| 点 | 我定的 | 理由 |
|---|---|---|
| 写方案的强度 | 固定“低” | 和你现在的设置一致；不固定的话会落到默认的“极高”，变慢变贵 |
| 写方案/备资料用 Codex，不看写测试是谁 | 固定 Codex | 现在的写方案本来就只会调 Codex，不是新限制 |
| 旧调度员设置 | 忽略，不清理 | 清理要改用户文件，收益为零 |
| 停用行政 | 按钮保留；停用后没人可聊，窗口停在团队页 | 不另造退路，免得又多一条要维护的通道 |
| Swift 外壳 | 窗口标题、两处占位文字、停用行政确认框，并且不再读老配置里的调度员（这样第 2、7 条才成立） | 外壳已经把“行政配好了”当作能聊天；改外壳要重装，范围尽量小 |

## 6. 已知风险（详见方案）

- 改动面跨：配置、团队检测、服务端、团队页、右栏、行政、外壳，加上测试。估计 10–15 个测试文件要跟着改（**推测**，动手后才知道准数）。
- 外壳是冻结的，改了要重装才生效；重装会退出应用，**必须确认没有卡在跑**。
- 我没有测过“固定低档写方案”的质量：施工单齐全时是转抄，影响小；没有施工单的卡，方案质量以前也是“低”档在写，不会比现在差，但这点没单独实测。
