# 方案 C1.6：复查收口（跑卡流程调整 · 第二批，插在 C2 前）

> 状态：**用户 11-18 批准**（Q1、Q2 都选 A）；同日用户依 pstack 评估补一条（第二节 4 条“先等全部测试跑完”），又采纳另一窗口意见把“上轮改好没有”改成按编号逐条回答（第二节 3 条）。起因见 [讨论-纠错与交接](讨论-纠错与交接.md) 四之三：C1 起复查“这次改的一律退回”却没有收口，CARD-003/004 从 25–37 分钟变成 2–3.5 小时；三轮复查每轮都挑出新的、越来越偏的边角（11→9→6 件），退满两次后把一堆技术条目丢给用户。
> 原则：不降低质量底线（严重的、改坏老功能的、测试写错的，照旧必退）；只是让“越挑越偏”的边角有去处，不再无限循环。

## 一、要做什么（一句话）

第 2 轮起复查只核对“上次退回的改好没有”和“新冒出的严重问题”；其余新边角自动记进以后再修和台账；退回用完后程序先自己分拣，只把真正要人拍板的事用一句大白话问用户。

## 二、具体规矩

1. **复查清单每条加一项“会不会碰上”**：常见 / 少见 / 极巧合（例：“恰好在两步之间被打断”算极巧合）。和级别分开写，复查员必填。
2. **第 1 轮复查照旧**：这次改出来的，不分轻重都退回（C1 口径不变）；但标“极巧合”的且不严重的，记以后再修，不退回。
3. **第 2 轮起（退回后的复查）**：
   - **按编号核对**（用户 11-18 采纳另一窗口意见，替代原先“比位置 / 比文字”的认法）：程序退回时给每个问题编号；第 2 轮交代里列出编号和现象，复查员在清单里加一段“上轮核对”，按编号逐条答“改好了 / 没改好”。程序只认这个回答：答“没改好”的照旧退回；**漏答的一律按没改好算**（宁严勿松）；整份结论是“通过”且问题为空时视为都改好了。
   - 新冒出的问题：严重的、改坏老功能的、测试写错的照旧退回；**其余记进以后再修和台账，不退回**（用户 11-18 定：Q1 选 A）。
4. **退回用完还没过时，程序先分拣**：
   - 剩下的都不严重 → **先等这一轮的全部测试跑完**（和复查通过时同一步）：全过才自动进“待验收”，验收说明写清“还剩 N 件小问题已记以后再修”（用户 11-18 定：Q2 选 A）；全部测试改坏老功能、超时或没跑成 → 不自动放行，停下交把关的人（用户 11-18 补：不能新开一条不跑完全部测试就进待验收的路）。
   - 还有严重的 → 停下，交给把关的人（现阶段 Claude 先看，给用户一句话建议），不把技术条目原样列给用户。
5. **停下时给用户看的**：一句大白话结论 + 一个推荐按钮；技术条目只放在“交接”里。

## 三、不做什么

不改退回次数上限（还是 2 次）；不改复查强度；不动全量测试、模型不回话、少重读（另卡）；不碰 C2 的内容。

## 四、改动范围（预计）

collab/dispatch.py（复查交代、收口判断、停下分拣）、collab/phase.py（停下显示）、collab/规则.md（复查员那一行加“会不会碰上”）、新测试。范围比 C1.5 小，预计一张卡 1 小时内。

## 五、待用户拍板

- **Q1 第 2 轮起新冒出的“中等、常见”问题**：A 记以后再修（快，推荐：第 1 轮已经全面看过，第 2 轮新冒出的多是边角）；B 照旧退回（严，但可能又收不住）。
- **Q2 退回用完、只剩不严重的**：A 自动进“待验收”，在验收说明里写清“还剩 N 件小问题已记以后再修”，你验收时一眼能看到（推荐）；B 照旧停下等你点“接受剩下的问题”。

## 六、怎么算做完

- 验收测试覆盖第二节 1–5 条；全部测试通过（Python 3.15，用程序现成的按文件同时跑）。
