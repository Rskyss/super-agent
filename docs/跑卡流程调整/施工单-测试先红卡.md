# 施工单 测试先红卡：写测试的交活后先确认新测试真的不过

> 依据 [方案-测试先红卡](方案-测试先红卡.md)（Claude 按用户 11-18 授权自批）。写给开发助手的施工方（写测试、写代码、复查）。
> 项目就是开发助手这个仓库。**验收测试已经写好**（`tests/test_redfirst_acceptance.py`），施工方**不许改**；写测试的只**补充**，写进新文件 `tests/test_redfirst_extra*.py`。
> 第五节那处共用测试工具的改动 Claude 已在建卡前改好，**不许再改**。

## 一、要做什么（一句话）

写测试的交活后，程序先跑一遍本卡测试；一跑就全过退回写测试的一次，再全过就停下交把关的人；改测试那轮不查；补测试那轮全过只提醒写代码的。只在真实跑卡时查。

## 二、允许改哪些文件

- `collab/dispatch.py`
- `collab/cli.py`
- `tests/test_redfirst_extra*.py`（写测试的新建）

**不许改**：`tests/test_redfirst_acceptance.py`、`tests/acceptance_helpers.py`，以及上面没列的任何文件。

## 三、具体做法

### 1. 开关（`collab/dispatch.py`、`collab/cli.py`）

- `run_card(..., red_check=False)`，原样传给 `_run_card`。默认关：老测试用假判定“永远通过”，不能被这个检查改变走向。
- `collab/cli.py` 的 `cmd_run` 里调用 `run_card` 时加：`red_check=ask_fn is None and os.environ.get("SUPERAGENT_NO_RED_CHECK") != "1"`（和旁边 `draft`、`progress` 同样写法）。

### 2. 第一步写测试之后查（`collab/dispatch.py` 的 `_run_card`）

在“第一步：测试员按验收标准先写测试”那一段之后、“第二步：开发员照着测试写代码”之前，`red_check` 打开且 `test_command` 不为空时，做下面这件事（写成一个函数，第一次跑和接着跑共用）：

1. 只看 `past`（`_after_revise` 之后的记录，追加要求生效后重新算）。
2. 找最近一次写测试的成功交活：`回复`、`src` 测试员、`ok` 为真、`step` 是“写测试”或“重写测试”。没有就什么都不做。
3. 这次交活之后已经有 `转人工` 且 `cause` 是“测试先红” → 把关的人点了接着跑：**不查，直接往下走**。
4. 这次交活之后还没有“先红检查” → 现在查：`judge_fn(test_command, cwd=worktree, timeout=_TEST_TIMEOUT)`，记一条：
   `record(cdir, "先红检查", src="程序", step=<这次交活的 step>, result=<判定结果>, summary=…)`。summary：过 →“还没改代码，本卡测试一跑就全过”；没过 →“还没改代码，本卡测试没过（正常）”；其他 →“还没改代码，本卡测试没跑成：<结果>（交给后面的判定）”。
5. 看 `past` 里结果为“过”的“先红检查”有几条（含刚记的）：
   - 最近一条检查不是“过” → 往下走。
   - 是“过”、共 1 条 → 退回写测试的重写一次：用现有的 `_tester_work(ask_fn, cdir, test_adapter, worktree, by_role.get("测试员", models), 1, test_command, revert_fn, "重写测试", prompt)`。交代 `prompt` 要写明：`{_READ_RULES}` + “你写的测试在还没改代码时一跑就全过，说明抓不到问题；也可能是新测试不在本卡测试命令跑的范围里（测试命令：…）。按任务卡 {needs} 的验收标准把测试改成现在会不过、等写代码的做完才会过的样子；现有代码确实已经做到的那条，在汇报里写明是哪条。只改测试文件，不改产品代码，改了也会被撤掉。” + `_run_hint(test_command)`。
     重写交成了 → 回到第 2 步再查一次（这次交活的 step 是“重写测试”）。没交成 → 照现有写测试没交成的办法处理（`_worker_failed`）。
   - 是“过”、已经有 2 条 → `_escalate(collab, cdir, card, "写测试的两次交的测试一跑就全过（还没改代码），抓不到问题，需要把关的人看：测试是不是写松了，或者现有代码已经做到了", cause="测试先红")`，`return card, None`。
6. 接着跑时：上次在重写测试派出后、交活前被打断（最近一条检查是“过”、共 1 条、之后没有“重写测试”的成功交活）→ 重新派重写测试，同第 5 步。

### 3. 补测试之后查（`collab/dispatch.py` 的 `_guard_tests`）

- 需要拿到 `judge_fn` 和开关：给 `_guard_tests`、`_dispatch_review_return` 加参数（`judge_fn=None, red_check=False`），两处调用方（连续跑、接着跑）都传进去。`_tester_fix`（改测试）**不查**。
- 补测试交成后，`red_check` 打开且 `judge_fn`、`test_command` 都有时跑一次本卡测试，记“先红检查”（`step="补测试"`），结果是“过”时，返回给写代码的交代改成：“\n\n写测试的补了测试，但在改代码前一跑就全过，没抓住这几条问题；别当成已经有测试守住，改完在汇报里写明怎么确认改好了。” 不重派、不停下。
- 不是“过”就照原来的交代。

### 4. 停下后的样子

- 停下用现有 `_escalate`，卡片“卡住了”、原因就是上面那句；按钮照旧（接着跑、继续改、先不做），**没有**“接受剩下的问题”（不是复查停下的）。

## 四、不做什么

不逐个测试文件查先红；不改复查、退回次数；不改写测试第一次的交代；不改页面；“改测试”那轮不查。

- `tests/acceptance_helpers.py` 的 `ProjectCase.setUp` 加了 `SUPERAGENT_NO_RED_CHECK=1`（和旁边 `SUPERAGENT_NO_DRAFT` 同理）：走真实命令行的集成测试用假 AI，测试命令一跑就过，不关会被这个检查改变走向。
