## 一、口径

1. **复查员必须按固定格式交结论**：回复最后附一段固定格式的清单。程序**只认这段清单**，不再从正文里猜。每条问题必须写齐：
   - 级别：严重 / 中等 / 轻微；
   - 来源：这次改的 / 原来就有的；
   - 类型：功能问题 / 测试写错；
   - 现象：一句大白话；
   - 位置：文件和行号；
   - **证据**：能实际跑的，写出跑的命令和看到的输出（标“实跑”）；跑不了的（文档前后矛盾、漏改的地方），标“推演”，写出对照的文件和行号。**不许因为跑不了就不报。**
2. **格式不合格时**：程序请复查员**按格式重写一次**，只改格式、不重新复查，几分钟、用量很小。还不合格：结论是“不通过”的，整段原文退回给写代码的；结论是“通过”的，卡停下由 Claude 看。**格式不合格一律不自动放行。**
3. **自相矛盾也不放行**：结论写“通过”，清单里却有“这次改的”问题，按“不通过”处理。
4. **每一轮复查都提醒老测试的变化**（现在只有“继续改”那一轮才提醒）：
   - 测试员改了或删了已有的测试，逐个列出，要求复查员核对；
   - 改动里给老测试**新加了“跳过”**（各种测试写法里的跳过都算），也逐个列出，要求复查员判断合不合理，**不合理就判不通过**；
   - **本卡测试员新写的测试文件里带“跳过”的，同样列出**、同样要求判断（用户 11-18 补：程序现在不检查新测试写完时是否真的不过，新测试一旦被跳过，测试命令照样显示通过）。
5. 后面的环节都只读这份清单：
   - 收口（退回 / 记台账 / 放行）；
   - 补测试的问题清单；
   - 停下时的提示和确认框；
   - 右栏复查格；
   - 中途打断后接着跑。
   C1 的规矩不变：这次改的一律退回，原来就有的（不严重的）记台账，严重的照旧退回。

## 二、你会看到什么变化

- 复查格的结论和停下时的提示，不会再出现“明明有严重问题却说都是小问题”“漏了一条就放行”。
- 偶尔会多出一步“复查员按格式重写”，右栏能看到，几分钟。
- 复查员挑的每条问题都带“怎么证明的”，交接里能看到命令和输出，或者对照的位置。
- 测试员要是给老测试加了“跳过”，复查一定会看到，不会悄悄混过去。

## 三、泼冷水

- **复查员可能不守格式**：模型偶尔会漏写、写错字段。所以有“重写一次”。第二次还不行，就按第 2 条保守处理，代价是偶尔多退一次或多停一次，不会漏放。
- **证据会让复查变慢一点**：要求“实跑”，复查员就要多跑命令。复查员本来就跑本卡测试，增加有限。具体多多少，跑一张卡再看。
- **“跳过”认不全**：我会覆盖 Python 自带测试、pytest、常见 JS 测试的跳过写法。项目自造的写法认不出，复查员仍然能从“老测试被改过”的清单里看到这个文件。
- **改的是程序最核心的一段**：C1 加的那套猜格式的认法（包括 Claude 的兜底）**整体删掉换新的**，不新旧并存。老测试里按旧认法写的会成批失败。Claude 先按新口径改好、逐个登记原因，再建卡。
- 和 C1 一样，**新规矩要放进项目、重装后，从下一张卡起才生效**，这张卡本身仍用旧规矩施工。
