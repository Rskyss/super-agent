## 二、这次发生了什么（事实，带证据）

### 2.1 写代码卡住（11-18 01:59–02:24）

| 时间 | 事 |
|---|---|
| 01:59 | 第 1 次退回后，派写代码的（qwen 壳 + DeepSeek V4.1 Flash） |
| 01:59–02:02 | 读了 3 分半代码，发 12 次请求，每次 14–30 秒回话，正常 |
| 02:02:47 | 第 13 次请求发出后，一个字没回；连接开着，进程空等（不占处理器） |
| 02:07 / 02:12 | 程序提醒“5 / 10 分钟没动静，可以再等等，或停下再接着跑” |
| 02:17 | 看门人 15 分钟到点停下，转人工；用户点“接着跑” |
| 02:18 | 新开的会话读完规则，发第 2 次请求，又一个字没回 |
| 02:23 | 用户点停下，把写代码的换成 agy（Gemini 4 Hydrogen 高），02:24 正常开工 |

排查：
- 同一时间 Claude 直接给同一服务发小请求（6 秒回）、6 万字流式请求（15 秒回完、最长停顿 8.8 秒），都正常；机器其他联网也正常。
- 卡住期间没有任何文件改动，不是写入失败，也不是我们程序出错。
- 结论：“Codex 壳接千问 Token Plan”这条路偶发请求石沉大海。**卡在服务端还是本机代理（连接走 198.18.x.x 代理地址）没查实。**
- 工具自己没有重发：Codex 对这类服务默认 5 分钟没回话才重发，看门人 15 分钟就停了，两者没配合上（这点是推断，没逐项验证）。

### 2.2 token 消耗（截图，CARD-004 进行到第 1 次退回后的写代码第 3 次）

| 环节 | token |
|---|---|
| 写方案 | 19.6 万 |
| 写测试（2 轮） | 280.8 万 |
| 写代码（3 次派活，其中 2 次卡住） | 988.6 万 |
| 本卡合计 | 1500.3 万 |

- 每次派活都是一个**全新的 AI 会话**，不记得上一轮读过、改过什么。

- 换了模型的新 AI（agy）开工 2 分钟读了 11 个文件，是从头摸。

## 三、现在已经有的（别重复造）

- **调度员交接资料**：开工时调度员读一遍，写下要改的位置、现在的写法、相关规矩（约 5000 字），写代码和复查都先读它。
- **退回只交要改的几条**：交代里写明“其他部分已经测过、复查过，不要重新核对，也不要重读整张卡和交接资料”。
- **退回后的复查只看改动、强度降一档**（C1）。
- **没动静提醒**：5、10 分钟提醒，15 分钟看门人停下。
- **工具升级提醒**：agy 升级时提醒去团队设置重新检测。

## 四、缺的（初步想法，待核对）

### A. 流程异常的纠错：由行政出面（对应原话 1、2）

现状：代码质量有纠错（复查退回、最多两次）；流程本身出岔子（模型不回话、写方案又加了全部测试、交代写歪）程序不会察觉，全靠 Claude 盯着、再让用户去点。

想法：
1. 行政分辨“模型服务没回话”（工具在空等）和“工具在干活只是没改文件”。
2. 前者直接给建议：“写代码的 DeepSeek 5 分钟没回话，像是服务卡了，建议停下换成今天跑得正常的 Codex，再接着跑”。
3. 停下后的提示也带这条建议。
4. 有记性：同一模型今天已卡过两次，下次派活前先提醒。
5. 能自动处理的自动处理：模型一两分钟没回话，工具先自己重发，不用等满 15 分钟整张卡停下。
注意（11-18 02:47 又遇到一次）：第 2 轮复查的 Codex（GPT-6.2-Sol 极高）也 5 分钟没动静，查下来是模型在“深想”（极高强度时想的过程不往外吐字），和 DeepSeek 那次“请求石沉大海”从外面看一模一样。所以“没回话”不能一刀切判成卡死：要按强度给不同的等待时长，或看服务有没有在回“还在想”的信号，判错了会把正常深想的复查打断。
6. 范围待定：方案里加了全部测试、方案测试命令和施工单不一致（观察 31、38）这类，是行政提醒、还是程序直接拦（C2 的 B2 已打算做后者）。

### B. 交接，少重读（对应原话 3）

按估计收益从大到小：
1. **同一模型退回重改时，接着原会话干**，不新开：它记得读过什么、改过哪里。已查：Codex（`exec resume`）和 agy（`--conversation`）都支持接着原会话；程序现在没用。换了模型就接不上，要靠下一条。
2. **每个角色交活时留几行“工作笔记”**：动了哪些文件、关键逻辑在哪几行、还有什么没弄完。下一个人（包括换进来的新模型）先读笔记。
3. **程序把“这一轮改了哪里”和问题位置直接写进交代**，少让 AI 自己翻。
4. 一次退回 11 件太多时，要不要分批交（待讨论，可能增加轮数）。

风险和拿不准的：
- 接着原会话干，对话会越来越长，单步更贵；要和“新开 + 读笔记”实测对比再定。
- 读代码本身省不掉：AI 没看到代码就改不了。能省的是重新摸“东西在哪”、重读规则和整张卡、对话越拉越长。
- token 按缓存价打折的比例、订阅额度怎么算，各家不同，没逐家核实。

### C. 停下时别把技术条目丢给用户（用户 11-18 原话：“以后这样的问题能不能够自行解决啊？突然这给我弄这么多我也看不懂。”）

事实：CARD-004 两次退回用完后停下，确认框列了 5 条技术边角（“四个反引号”“续跑派活”这类），严重的还没标级别，用户看不懂、没法判断，只能问 Claude。三轮复查 11→9→6 件，都是新挑出来的、越来越偏的“恰好在某两步之间被打断”情况，不是没修好。

想法：
1. 复查清单每条多写一项“会不会真碰上”（常见 / 少见 / 要极巧合），和级别分开。
2. 退回用完后，程序先自己分拣：要极巧合才碰上的、轻微的，直接记进“以后再修”和台账，不问用户；真会碰上的严重问题，由一个把关角色（现阶段是 Claude）自己补，补完再复查。
3. 只有影响产品取舍的（要不要这个功能、能不能接受某个用户看得到的毛病）才问用户，而且用一句大白话 + 一个推荐按钮，不列技术条目。
4. 停下提示的判断要按清单：三轮挑的是不同问题时，不能说成“同一个问题反复出现、换模型”（见观察第 43 条）。

和规矩的关系：符合已有记忆“技术小问题别问用户”（11-17）；C1 只做到了“原来就有的”不问，“这次改的”边角还是全退回、退完就丢给用户。

### D. 一张卡跑太久、卡死没人发现（用户 11-18：“这种事情不要发生了，因为这一次 C1.5 改的时间太久了。”）

C1.5 从开工（约 01:15）到放进项目（04:54）约 3 小时 40 分钟，时间花在：

| 原因 | 大约耗时 | 谁的责任 |
|---|---|---|
| 复查收不住：三轮都挑出新的、越来越偏的边角（11→9→6 件），每轮补测 + 写代码 + 复查约 45–60 分钟 | 约 2 小时 | 流程设计 |
| 写代码的模型（DeepSeek）两次请求石沉大海，各等满 15 分钟 | 约 25 分钟 | 外部服务 + 流程没自动重发 |
| 全部测试被新代码卡死：程序的全量三轮都因复查不过被中途叫停，从没跑完过，所以没发现；Claude 验收时只等后台结束、没盯中途 | 约 40 分钟 | 流程设计 + Claude |
| Claude 建卡前给老测试做的转换漏了一类（命令行式假复查员），验收时才发现、现补 | 约 15 分钟 | Claude |

防再发（初步，待核对）：
1. **全量测试每个文件限时**，超时就记下是哪个、接着跑别的，不再整体卡死；程序的全量报告里直接写“哪个测试卡住了”。
2. **放行前必须有一次跑完的全量**：现在复查不过就叫停全量，导致最后一轮之前全量从没跑完；至少在第 2 轮复查时让全量跑完一次，提前暴露“改坏老功能”。
3. **复查收口**：退回后的复查只核对上一轮的问题有没有改好，加上新冒出的严重问题；要极巧合才碰上的边角直接记以后再修（和 C 节一起做）。
4. **模型不回话自动重发**（A 节第 5 条）。
5. **Claude 自己的规矩**（立即执行，不等功能）：后台长任务一律同时开监看；建卡前在旧代码上把全部测试跑一遍，确认转换覆盖了所有老测试的写法。
7. **测试统一用开发助手实际运行的 Python**（用户 11-18：“老的也要更新”）：装好的开发助手跑在 Python 3.15 上，但卡片测试命令里的 python3 在开发助手环境里会落到老的 3.9，两边不一致；改成统一用 App 那个。
6. **卡切小**：C1.5 一张卡改了跑卡程序里十几个环节，复查面太大；以后同类改动拆成 2–3 张。

## 四之三、为什么现在比原来慢这么多（11-18 用户：“原来开发根本就没有这么久，到底哪里出了问题”）

数据：CARD-001 37 分钟、CARD-002 24 分钟；CARD-003（C1）2 小时、CARD-004（C1.5）3.5 小时。分水岭是 C1。

1. **C1 的规矩是 Claude 设计时没想收口**（主因）：用户要的是“技术小问题别丢给我、自己修掉”，Claude 翻译成“这次改出来的不分轻重一律退回，先补测试再改”。复查员（极高强度）每轮总能挑出新边角，于是每张卡都退满两次、再停下丢给用户——每轮多了补测，又比原来长。用户的要求没错，是 Claude 的方案缺“什么时候算够了”。
2. **这两张卡改的是跑卡程序自己最复杂的那个文件**（collab/dispatch.py，约 3000 行，C1.5 一张卡加了 1300 行）：越改越大，复查员越能找出边角。普通功能卡（CARD-002 改界面）只要 24 分钟。架构上这是警讯：跑卡核心在“补丁叠补丁”，后面要拆分整理，不然每张流程卡都会越来越慢。
3. **Claude 自己的执行失误**：没用程序里现成的快速全量（2.5 分钟），自己一个个慢跑（16 分钟）还反复重来；卡死干等 40 分钟；建卡前漏转换一批老测试。
4. **外部**：模型两次不回话。
