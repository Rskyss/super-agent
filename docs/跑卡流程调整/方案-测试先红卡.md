# 方案：测试先红卡（写测试的交活后，先确认新测试真的不过）

> 2026-11-18 · 口径用户 11-18 已定（任务清单-第二批“11-18 调整”一节、观察记录第 37 条）；用户同日要求 Claude 一路做完、技术问题自己定，**本方案由 Claude 按授权自批**。
> 判大小：中（只动跑卡流程里“写测试交活之后”这一段）。施工交开发助手跑卡。

## 1. 你能感受到的变化

1. **写测试的交活后，程序先跑一遍本卡测试**。还没改代码就全过了，说明测试抓不到问题（或者新测试根本没被测试命令跑到）：退回写测试的**一次**，说清原因。
2. **退回后再全过，就停下交把关的人**（卡片显示“卡住了”，写明“写测试的两次交的测试一跑就全过”）。把关的人看过觉得没问题（比如现有代码确实已经做到了一部分），点“接着跑”就直接交给写代码的，不再查。
3. **“测试本身写错了”那种改测试的轮次不查**（改完的测试本来就可能直接过）。
4. **复查退回后补测试的那一轮**：也查一次；一跑就过就告诉写代码的“补的测试没抓住问题，别当成已经有测试守住”，**不退回、不停下**（复查本身还会再看一轮，退回次数有上限，不在这里再加一道停）。——这条是 Claude 定的，见第 4 节。

## 2. 怎么做（技术，Claude 自批）

| # | 做什么 | 改哪里 |
|---|---|---|
| 1 | 写测试（第一次、追加要求那次）交活后，用判定测试的同一个办法跑本卡测试命令，记一条“先红检查”（结果、哪一步） | `collab/dispatch.py` |
| 2 | 结果是“过”：本轮第一次 → 派写测试的重写一次（只改测试）；已经退回过一次 → 停下转人工，标记“测试先红” | `collab/dispatch.py` |

| 4 | 接着跑：上次因“测试先红”停下、之后没有新的写测试交活 → 直接交给写代码的；上次交活后还没查就被打断 → 先补查 | `collab/dispatch.py` |
| 5 | 复查退回后的“补测试”交活后查一次，“过”就给写代码的交代加一句提醒；“改测试”不查 | `collab/dispatch.py` |

## 3. 影响面

1. 动的：跑卡流程里写测试交活之后、交给写代码的之前；补测试之后给写代码的交代。
2. 老测试：大量老测试用“判定永远通过”的假判定，开关默认关，不受影响；走真实命令行的集成测试由 Claude 在共用测试工具里设 `SUPERAGENT_NO_RED_CHECK=1`（建卡前改好、登记在施工单第五节）。
3. 页面：停下的卡照旧显示“卡住了”和原因；按钮照旧（接着跑、继续改、先不做），没有新按钮。
4. 时间：多跑一次本卡测试（通常几十秒）；退回那次多一轮写测试。
5. 已知局限：检查的是“整条测试命令全过”。Claude 预先写好验收测试的卡，验收测试本身就不过，所以写测试的补的测试再松也查不出来——这类卡由 Claude 写的验收测试兜底，复查员也会看。
6. 和已批准文档：符合任务清单-第二批“测试先红卡”口径；不矛盾。要重装开发助手才生效。
7. 不做：不检查每个新测试文件各自先红；不改复查、退回次数；不改写测试的交代（除退回那次的说明）。
8. 证明：验收测试（见施工单）；放进项目后下一张真实卡跑的时候看流转里有“先红检查”。

## 4. Claude 替你定的（事后可改）

- 补测试那一轮一跑就过：只提醒写代码的，不退回、不停下（理由见第 1 节第 4 条）。
- 检查用整条本卡测试命令，不逐个文件查（理由见第 3 节第 5 条）。
