# 方案：第一批“别白跑”（外部项目试跑修复）

> 依据 [需求共识](需求共识.md)。问题编号对应 外部项目观察-train（本机笔记 docs/流程数据/外部项目观察-train.md，不进 git）。

## 一、你会看到什么变化

### 1. 测试文件自己写错时，交回测试员（⑫）

**现在**：测试没过、报错全在测试文件自己身上（比如 train 那 3 处写法错误），程序照样退给写代码的。写代码的不许改测试，只能原地打转，直到返工次数用完停卡。train 白转了 3 轮、约 17 分钟、约 460 万 token。

**改后**：程序看测试没过的输出，报错的位置**全部**落在本卡登记的测试文件里、一处都不在产品代码里时，就判为“测试本身写错了”，派写测试的只改测试（复查说“测试写错了”时已有的那条路，原样复用），改好后再判定。流转里多一条“测试文件自己有错，交回写测试的改”。
- 只要报错里有一处在产品代码里，就照旧退给写代码的（宁可少转，不可错转）。
- 交回测试员最多 2 次，还不过就停卡转人工，免得在测试员这边打转。

### 2. 停卡、接手后接着跑，先重新跑一遍测试（⑭）

**现在**：有人接手修好、说“已全过”，接着跑时程序不重新判定，直接把停卡前的旧报错交给写代码的，让它再白跑一轮。

**改后**：接着跑时，如果上次停在“测试没过”，程序先在副本里把本卡测试重跑一次：
- 过了 → 直接进复查（流转写“接着跑：本卡测试已经过了，直接复查”）；
- 没过 → 用**这次新跑出来的**报错派活，不用旧的。
- 多花的时间就是跑一次本卡测试（train 约 1 分钟）。

### 3. 接着跑时，把前情交代给下一棒（⑧ ⑮）

**现在**：停卡换人、接手之后接着跑，派给下一棒的话和第一次一字不差，不说副本里已经有什么、谁改过什么。train 里 DeepSeek 因此把来龙去脉说反了，在汇报里冤枉了接手的人。

**改后**：凡是“接着上次中断处继续”派出的活，末尾多一段“前情”：
- 这张卡停过几次、最后一次为什么停；
- 有人接手过的话，接手人留的说明原话；
- 副本里已经改过的文件清单（测试文件单独列出，写明“已有测试，请在它基础上接着做，不要推倒重写”）；
- 同一岗位上一棒最后的汇报（有的话）。

### 4. 范围检查认得测试员中途新加的测试文件（⑲）

**现在**：测试员在复查退回后新建一个测试文件，程序已经登记进测试名单，但写代码的交活时，范围检查还拿开跑时的老名单比，把这个文件当成“范围外改动”撤掉，再从备份恢复，流转里留下两条冤枉写代码的记录。

**改后**：每次测试员交活后，范围检查用的名单跟着更新。写代码的没动测试文件，就不会出现这两条记录。

### 5. 本卡合计下面加总耗时（⑪，用户点名）

右栏“本卡合计 N token”下面加一行耗时。怎么算待你选（见第五节第 1 题）。

### 6. 写测试的规矩补两条（2026-11-23 用户“把这两处给修改完”后追加）

- 交活前单独跑一次类型检查或编译检查，测试文件自己的写法错误要清干净（只允许“产品还没写”这类报错）——从源头少出 ⑫。
- 有数据库的项目，假数据照数据库结构定义写，查不存在的字段要像真库一样报错（⑰）。
只改规则包里写测试的规矩文字，不改程序。

## 二、不改的

- 第二批（显示和记录）、第三批（外部项目兜底）不在这次。
- 不改 train 项目任何文件；不在 train 卡跑着时重装开发助手，重装前先问你。

## 三、泼冷水

- **第 1 条只认“报错位置”**：测试命令的报错里得带文件名和位置（类型检查、大多数测试工具都带）。有的工具报错不带位置，程序就认不出，照旧退给写代码的——这种情况不会变坏，只是没改善。
- **第 1 条可能误判的情况**：产品代码里少了一个函数，类型检查有时只在测试文件里报“找不到这个函数”。这种其实该写代码的补。为防误转，测试员那边的话会写清：“如果你看下来是产品代码没写，不要硬改测试，直接回复说明”，程序看到这句就转回写代码的。这一点我**没有十足把握**能覆盖全，要看实跑。
- **第 2 条多花一次测试时间**：网页项目打包慢的，可能 1–2 分钟。
- 这几处都改的是跑卡主流程，牵涉老测试较多，我估计约一天（推测）。

## 四、怎么验收

- 每条先写会失败的测试，改完变过；全部测试全过。
- Codex 极高独立复查通过。
- 重装后拿一个练习项目，故意让测试文件带一处写法错误跑一张小卡：应看到“交回写测试的改”而不是退给写代码的；再试一次停卡、接手、接着跑：应看到先重跑测试、直接进复查。右栏能看到总耗时。
- 台账登记。

## 五、要你拍板的（2026-11-23 已拍板：1 选 A 只算干活时间；2 选 A 先不改，⑦ 记为已知问题；方案批准）

1. **总耗时怎么算？**
   - A（推荐）：只算真正在干活的时间——中间停卡、等你点按钮的时间不算。好处：反映各模型真实效率；train 这张卡到停下时大约 2 小时（三段：16:24–16:40、16:40–17:24、17:26–18:20）。
   - B：从第一次开跑到现在的钟表时间，停着等人的也算。好处：反映这张卡拖了多久。
   - C：两个都显示。
2. **Codex 隔离拦测试工具（⑦）改不改？** 我实测了：Codex 默认的隔离不让程序在本机开“通信口”，网页项目的测试工具一启动就被拦；打开 Codex 的“允许联网”就不拦了，但同时也放开了上网。三个模型这次都自己申请放行绕过去了，每次只多花几秒。
   - A（推荐）：先不改，记为已知问题。损失很小，不值得为它放开上网。
   - B：只对网页项目（有 node 测试工具的）打开“允许联网”。
   - C：所有项目都打开。

## 六、技术说明（可跳过）

- 第 1 条：在判定没过、退回写代码之前加一道“报错位置都在测试名单里”的判断，命中就走现有 `_tester_fix`（复查说测试写错时用的那条），并单独计数上限 2。
- 第 2 条：续跑入口在派写代码前，若最后一条判定是没过、之后有“接手”或卡从“需Claude介入”恢复，先调一次判定函数。
- 第 3 条：续跑时派活的话里拼一段前情，素材全来自流转记录和副本改动清单，不新建记录文件。
- 第 4 条：`effective_allowed` 在每次测试员交活后按测试名单重算。
- 第 5 条：用流转里的“开跑”“停下/转人工/待验收”等记录算时段，界面只在右栏合计下加一行。
