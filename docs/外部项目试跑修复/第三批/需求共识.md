# 需求共识（定稿，用户 11-24 批准）：第三批“外部项目兜底”

> 来源：train 试跑观察 ③⑯⑰⑱⑳。11-23 22:50 用户外出时授权“卡做完后把问题都修一遍”。改动面大，先出这份，**等用户批准再写方案，没写代码**。
> 第 2 稿（11-24）：用户选了 ⑯“项目里配一次”、③“硬拦”；⑱⑳ 让我参考 pstack 的做法；“AI 在真实页面上操作测试”这一关等 Codex 这次实测完再单独定，不放在本批。

## 一、要解决什么（大白话）

1. **⑯ 网页项目没有“全部测试”兜底**（最要紧，已实证）：开发助手的“全部测试”只认 Python 项目，train 每张卡只跑自己那一个测试文件。CARD-003 把 CARD-001 的测试改坏了，卡里没人发现，Gemini 合并后才查出来。
2. **③ 改界面的卡没人看页面**：施工单 02～05 都写了“放进项目前必须停下对照原型图看页面”，开发助手不会拦，五张卡都没看页面就放进了项目。
3. **⑰ 测试用的假数据和真实数据表对不上**：第一批已经加了规矩，没有程序检查。
4. **⑱⑳ 复查在同一处来回打地鼠**：CARD-002（读取计时）、004（遮组号）、005（并发覆盖）都在同一处退回 3 轮，根子是施工单没定规则，写代码的只能一处处补。靠 Claude 在信箱提醒、Gemini 定了规则才收住。

## 二、定下来的做法

### ⑯ 网页项目也跑“全部测试”（用户定：项目里配一次）

- 每个项目在自己的设置里配一次“全部测试命令”。train 可以配成 `tsx --test tests/*.test.ts && pnpm typecheck`。配好后每张卡自动使用，不用每张施工单都写。
- 配了：复查的同时在后台跑，和 Python 项目现在的做法一样。没过就退回写代码的，并写明是哪条老测试坏了。
- 没配：照旧跳过，右栏写明“这个项目没配全部测试，没有兜底”。

### ③ 要看页面的卡，不看不让放进项目（用户定：硬拦）

- 施工单“验收”一节写了“放进项目前要看页面 / 对照原型图”的卡，复查通过后不进“可以放进项目”，而是停在“等看页面”。右栏列出施工单写明要对照的原型图。
- 人看过之后点“已看过”，并选“和图一致”或“有出入（写一句）”。点完才能放进项目。“有出入”的那句话记进卡片，可以退回写代码的去改。
- 谁来看：第一版就是人（或者人转交给 Codex 这类能点页面的 AI，点“已看过”的仍是人）。

### ⑰ 假数据对不上真实数据表：不做程序检查（用户 11-24 同意）

- 要做准，得读懂各家数据库的迁移文件，成本高，还容易误报。这类错到真实页面测试时一定会暴露，真正的兜底是以后的“AI 在真实页面上操作测试”。先保留第一批的规矩。

### ⑱⑳ 同一处来回退回：照 pstack 的思路，看“是不是同一个根”，不数轮次

**pstack 是怎么做的**（11-24 重新读了源码 cursor/plugins/pstack）：
- 它不设“退回几轮就停”的数字，看的是**是不是同一个根**。复查意见要先把同一个根上的问题合并，修的时候要“修这一类，不修这一处”，把同类毛病都找出来。
- **同一种补法第二次出现，就停下来回去重新设计，不再接着补**。原话是“补丁反复出现就重新设计”，它整套规矩都用“第二次”当门槛。
- 第一次做完整复查；之后每次修完，只派一个人看这次改的地方，不再全面复查一遍，免得越挖越细。
- 复查员提的问题必须跑出来证明，比如一条会失败的命令，或者一段复现过程。“以后改了别的才会出事”的风险不算问题。
- 真卡住时停下，写清楚为什么卡住，不要原地打转。

**对照我们现在的情况**：
- 后两条我们已经有了：第 2 轮起复查降档，复查意见要附证据。
- 缺的是前两条：没有“合并同根”，也没有“同一个根第二次出现就停下改设计”。所以 train 那三张卡都是同一个根退回了 3 轮。

**定下来的做法**（11-24 用户确认，用装修打比方：施工单是给师傅的要求清单，写代码的是师傅，复查的是监理）：

复查员退回时，每个问题多写一栏“是哪一种”，分成两种处理：

1. **要求没写清楚**（施工单没定这条规则，或者规则之间冲突）：
   - 同一张卡**连续两轮**退回的问题指向同一条没定的规则，就不再派写代码的去第三次。卡停在“需要定规则”。
   - 右栏写明：是哪条规则、两轮各退了什么。同时让起草的 AI 先拟 2～3 个规则选项，写规则的人只要挑，不用从头想。
   - 谁来挑：纯技术规则（比如两人同时改以谁为准）由写施工单的人定，train 是 Gemini，开发助手自己的卡是 Claude；影响用户体验的（比如匿名要做到什么程度）交用户定。
   - 规则定好后，用“不满意，继续改”写进去（记成追加要求），写代码的照新规则改。（11-24 用户同意改：原写“补进施工单也行”，但接着跑用的是开工时的旧副本，写代码的读不到新补的施工单，确认复查查出，收回这条路。）
   - 用户的理解（原话大意）：写规则的人有盲点，开发中暴露出来，就把问题交回写规则的人重新定规则，再接着跑，这样反而跑得起来；不要规则一直没写，下面一直跑、一直错。
2. **要求写清楚了，是写代码的做错了**：
   - 同一处**连续两轮**做错，自动换**备份写代码的**（另一家模型）来改，不停下、不问人。
   - 对规则没写清楚的情况，换模型没用，只会各猜一种答案，所以备份只用在这里。
3. 只错一次的，照常退回。

按 train 的记录，CARD-002、004、005 都是第一种，按这个做法会在第 2 轮后停下来定规则，比实际少跑 1 轮写代码和 1 轮复查。

**起草的“继续改”变成重新设计（⑳ 另一半）**：起草的“继续改”比原施工单的范围大很多时（新增的要改文件超过原范围一半，或者改了验收要求），标“这是重新设计，请先看”，不直接开跑。

## 三、明确不做

- 不碰 train 的文件，不替 train 定产品取舍。
- 本批不做“AI 在真实页面上操作测试”这一关，等 Codex 这次实测结果出来，单独出需求共识。
- 不做浏览器自动点页面（③ 第一版只做“停下 + 人确认”）。

## 四、怎么算做完

- 先写会失败的测试，全部测试全过。
- Codex 复查最多 3 轮。第 3 轮后还剩中等以上问题就停下问用户，不自己记成取舍；第 3 轮后为了通过做的修改，补一次只看这些修改的确认复查（规则包《复查和验收》）。
- 重装后拿练习项目各走一遍：网页项目配全部测试、要看页面的卡被拦住、同根两轮停下。
- 台账登记。
