# 产品架构设想

**状态：** 💡 用户提出的整体方向（2026-11-07），还不是已批准的方案。以后每批方案都要说明自己落在哪一层。讨论过程见 [远期设想.md](远期设想.md) 末尾。

## 用户原意

收集能力：把各订阅平台、产品的 CLI 或 API 导进积木库，形成各种各样的能力，并保持每块都能用。再把这些能力串起来，为业务服务。

## 分层

```
前台（行政）：听用户说要办什么，推荐用哪些积木，请用户点头
    ↓
业务 ← 串联 ← 积木库 ← 收集能力
       ↑                 ↑
     把关         授权和花费（贯穿每一层）
       全程留痕
```

| 层 | 做什么 | 现在有没有 |
|---|---|---|
| 收集能力 | 判断一个订阅或平台能不能收；导入它的 CLI、插头（MCP）或 API | 没有，Codex、Cursor、agy 是写死的 |
| 积木库 | 每块积木按统一规格说清五件事：能做什么、怎么接、要不要密钥、能不能用、会不会替用户动手；定期检测，坏了用大白话说明 | 只有“检测”按钮 |
| 串联 | 把几块积木按流程接起来 | 只有写代码这一条，写死的 |
| 业务 | 写代码、出行规划、写稿等 | 只有写代码 |
| 前台 | 聊清需求，推荐积木，请用户点头 | 有（行政）。串联交给强的 AI 助手，不交给行政用的便宜模型 |
| 把关 | 每条串联写明哪一步由用户点头，或者按什么条件检查 | 只有写代码的测试 |
| 授权和花费 | 会动手的积木先问用户；看得到花了多少额度、费用 | 有确认弹窗，没有花费统计 |
| 全程留痕 | 谁做了什么都有记录 | 有 |

## 要记住的事实和判断

- 不是每个订阅都有 CLI。有 CLI 的主要是写代码类的 AI（Codex、Claude Code、Gemini、Cursor）；服务类平台多数提供 MCP 或 API（例如高德只有 MCP）；不少订阅只能在网页或 App 里用，收不进来。具体是哪几家，要逐家核实。
- 只有 API 的平台，由超级助手先造一个转接头再收。
- “保持能用”是长期的活：平台会升级，密钥会过期，额度会用完。
- 让 AI 评 AI 靠不住，非代码业务要单独设计“把关”（证据见 ../按需求大小调配/多模型协作调研.md）。
- 先后顺序：积木库 → 用一次真实组合验证 → 自由串联 → 通用的把关和花费。

## 例子：豆包 C 端订阅（2026-11-07 核实）

- 用户问能不能把手机上订阅的豆包“反向弄出来”画图、做视频。结论：不收。豆包用户协议（2026-09 版）第 5.1.1 条禁止使用未经授权的插件、外挂、第三方工具，第 5.1.2 条第（9）项禁止反向工程。另有封号、随版本失效的风险；超级助手自带这个功能，等于对外发放违规工具。
- 替代：火山引擎“火山方舟”开放同系列模型（画图 Seedream、视频 Seedance；Seedance 2.0 于 2026-04-14 开放接口，纯生成约 1 元一秒）。需要火山引擎账号、实名认证和 API Key，按用量另付费，豆包会员额度不通用。已有非官方的开源 MCP（github.com/nsmao-com/seedream-mcp），用前要看过代码；也可以由超级助手造转接头，作为“只有 API 的平台”的第一个例子。
- 规则：C 端订阅只有官方给了 CLI、MCP 或 API 才收；没有就找同一家的官方开放平台替代，不做破解，也不模拟点击。

## 安装积木的流程设想（2026-11-07）

用户原意：用户不用手动装。想装什么、或者不知道该用什么时，问行政（DeepSeek）；行政告诉他有哪些选择，并协助安装。动手的可能是行政，也可能是行政指派的 Codex。

Claude 的建议分工：
- 推荐装什么：行政。只给建议，不动手（行政不能运行命令是有意设的安全线）。
- 推荐清单里的积木：程序按事先测过的固定步骤装，不靠 AI 临场发挥。
- 清单外的积木：派 Codex 照官方说明装，有风险的动作照样弹窗。
- 注册账号、实名认证、付钱、复制密钥：用户亲手做，行政一步步带。
- 装完：程序自动检测并试用一次，成功才放进积木库。

流程：用户提出 → 行政列出选择（是否官方、要不要钱、要准备什么）→ 用户点“帮我装”，出现安装单（装什么、从哪来、要准备什么、会不会替你动手、谁来装）→ 需要亲手做的由行政带 → 程序或 Codex 安装，右栏显示进度 → 试用成功，放进积木库。

规矩：
- 密钥只填专门的密钥框，存进钥匙串，不在聊天里贴（行政聊天内容会发给用户选的服务商）。
- 装之前先亮出来源，官方和网友做的分开标；推荐清单里的事先看过代码。
- 没试用成功不算装好。

## 拖拽连线搭流程（2026-11-07 用户设想）

用户原意：积木库是单独的页面，展开后能看到各种 API、CLI。以后搭业务流程时，把积木拖过来、连起来就行。例：写文章的人拖进写作用的 CLI，需要查资料就再放一块“查内容”的 API 积木，一个流程里可以穿插各种能力。

借鉴（2026-11 核实）：
- n8n：画布看起来友好，但每两块之间要手动对数据格式，评测普遍说不懂技术的人很吃力。后来加了“用文字描述，AI 生成流程，再在画布上改”。
- 扣子：原来主打拖拽搭工作流，现在主推“AI 生成式工作流”。文字描述后 AI 生成，可以用文字改、框选节点改，也可以在画布上改；拖拽版收进“回到旧版”。
- 结论：行业从“用户自己画”转向“AI 画好，用户看着改”。拖拽留着，但只做查看和微调，不当主要入口。

Claude 的建议：
- 积木库做成单独页面，按“AI 助手 / 工具插头 / API”分栏，积木做成卡片，以后可以直接拖到画布上。
- 搭流程：用户对行政说要做什么 → AI 生成流程，画布上显示积木和连线 → 用户拖动换一块、加一块 → 两块之间的数据怎么对接由 AI 处理，不让用户填格式。
- 画布属于“串联”这一层，排在积木库之后；第一批先做积木库页面，不做画布。

## 两层：连接和能力（2026-11-07 用户提出，作为积木库核心设计）

用户原意：最底层是 CLI；上一层是能力，可以从 CLI 里把能力提出来，由用户通过行政来塑造。例：Codex 能出图，就单独做一块“Codex 出图”，流程里专门调用它；写代码的另做一块“Codex 写代码”。

- 连接：一个 CLI 或一个 API，只管怎么接进来、能不能用。
- 能力：从连接里提出来的专项用途，流程里拼的是能力块，不是 CLI。
- 好处：一个订阅能拆成多块能力；换底层连接，流程不用改；现有团队的写测试、写代码、复查三个岗位就是第一批能力，改造它们就能马上真用上；和 Claude、扣子的“技能”做法一致。
- 一块能力要写清：底下用哪个连接、固定交代、你给它什么、它交回什么、怎么算成功（程序检查）、允许它做什么、花谁的额度。行政起草，用户确认，程序试做一次成功才放进积木库。
- 提醒：“只做某件事”靠交代、权限和结果检查，不是绝对保证；Codex 出图要先实测（订阅能不能稳定出图、额度上限），没测过。

## 能力文件包：用现成的“技能”标准（2026-11-07）

用户原意：比如接入了 Codex 和 Claude，以后可以单独抽离出各种能力，其实就是建一个提示词目录或文件，也就是“能力文件包”。

核实（2026-11）：
- 行业已有标准 Agent Skills：一块能力是一个文件夹，里面一份 SKILL.md（名字、什么时候用、具体怎么做），可附脚本和资料。Anthropic 2025-12 发布，2026-10-22 捐给 Linux 基金会下的 Agentic AI Foundation；据报道 70 多个工具支持，包括 Codex、Claude Code、Cursor、Gemini CLI、ChatGPT。
- 存放位置：Claude Code 放在 `.claude/skills/`，Codex 放在 `.agents/skills/`（个人级 `~/.codex/skills`）。
- 社区已有让 Claude Code 借已登录的 Codex 出图（gpt-image-2，用 ChatGPT 订阅额度）的技能（codex-bridge），未试用。

Claude 的建议：
- 直接采用这个标准，不自创格式：Codex 和 Claude 通用，现成技能可以拿来用，换 AI 也大多能接着用。
- 一块能力 = 标准技能文件夹 + 超级助手自己的“能力卡”。能力卡写标准里没有的内容：底下用哪个连接、输入和输出、程序怎么检查成功、允许做什么、花谁的额度。
- 说明文件只是交代，AI 不一定照做；“只做某件事”要靠权限和程序检查兜底。
