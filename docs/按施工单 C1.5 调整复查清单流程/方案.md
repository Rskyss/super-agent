# 拆解方案

## 要做什么（一句话）
按 C1.5 把固定格式的复查清单接进跑卡流程，让退回、补测、停下、右栏和续跑都按清单办。

## 拆成几步，每步做什么、产出什么
1. 先读 C1.5 施工单和现有验收测试，找出派复查、记结论、停下和续跑各自从哪里进。
2. 看现有验收还漏了哪些容易出错的情况，优先补最后一个 JSON 块损坏、后续轮漏提醒或续跑读错清单的用例，补测只放进允许新建的测试文件。
3. 在 collab/dispatch.py 加 read_review_list，只读最后一个 JSON 代码块，按施工单核对结论、问题项的六个字段和规定取值，实跑要有命令和输出，推演要有带扩展名的文件和行号，不通过要至少有一条问题，校验失败就返回原因。
4. 更新每轮复查的交代，要求第一行写结论、末尾附 JSON 清单，保留施工单规定的提示字样和老问题的说明，并提醒复查员跑不了也要报。
5. 每轮都提醒复查员哪些老测试被改过，并列出副本里相对 HEAD 新增及未提交的新测试文件中的跳过写法，带上文件、行号和内容，提醒逐条判断、不合理就判不通过，同时避免把普通测试名识别为跳过。
6. 能读出结论但清单不合格时，只请复查员按固定格式重写一次，附上原回复和错误原因并说明不用重新复查，仍不合格就按原结论处理，原结论不通过则整段原文退回，原结论通过则以“复查结论格式不合格，不能自动放行”停下转人工，读不出结论则沿用现有流程。
7. 用有效清单决定放行或退回，这次改出来的、严重的、测试写错的任意命中一项都要退回，即使清单结论写了通过也一样，其余原有问题沿用 C1 的台账流程。
8. 把有效清单存进复查结论和转人工记录，从清单生成给写代码的人和写测试的人的交代，每条带现象、位置和证据，测试写错派改测试，其余退回问题派补测试，两种都有就都派。
9. 两次退回用完后按清单判断是否只剩轻微问题并生成停下提示和“继续改”草稿，续跑则从最近一条复查结论的清单取要改的问题。
10. 在 desktop/view.py 用最新一条复查员回复之后的复查结论更新右栏，通过显示完成、退回显示失败，没有复查结论的老卡沿用原显示。
11. 在 collab/phase.py 优先从转人工记录的清单生成停下时的问题列表，显示级别和现象，没有清单的老卡沿用原显示。
12. 把复查轮数改为只数复查结论记录，并要求写测试的回复后还得有对应步骤的“测试收尾”记录才算完成，收尾记录在还原越界改动、登记测试和更新快照之后写。
13. 整理失败测试的简短输出，去掉失败块之外以“- ”开头的日志，每个失败块保留标题、调用栈里的测试文件那一行和最后几行。
14. 保留 C1 的正文识别函数并注明仅供无清单老卡显示和测试转换使用，同时把规则第六节的复查员要求改成首行写结论、末尾附带齐六项和证据的清单。
15. 核对改动范围后只执行 test_command 里的三段测试，确认全部通过，若老测试确需按新规则调整就报告给复查方判断，全量测试由程序在复查阶段另行运行。

## 你会看到什么结果
用户在右栏能看到最终复查判定，格式有误时会先看到一次重写请求，仍不合格时会看到整段退回或转人工停下；本卡规定的三段验收测试全部通过。

## 明确不做什么
不改放进项目时存记录的位置、写方案、开工弹窗或验收记录，不改两次退回的上限，不改允许范围外的文件、现有验收测试、转换工具或已接上工具的老测试，不删 C1 的老认法，不追加全量测试命令。

## 需要你确认的问题
无

## 做完后怎么看结果
打开「超级助手」，选中项目和一张跑到复查的卡，看右栏的复查格是否按最终判定显示通过或退回，卡停下时再看右栏的问题清单是否列出了实际级别和现象。
