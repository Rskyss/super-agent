# 需求共识：开发助手显示 token 用量

> 2026-11-17 · 用户：“第一张卡就是给开发助手做一个 token 的计算”“就是累计用了多少”“不要写钱，就是 token 消耗就可以”。本文是对齐结果，**待用户批准**；批准后写《方案》和《任务清单》。
> **判大小：大**（跨协作包取数、卡片记录、右栏显示、行政对话，命中“跨多个页面或模块”）。这是**新规范下的第一个真实任务**，做完要在规范附录 D 填第一条使用记录。

## 1. 要做什么

开发助手现在**不知道每一步花了多少 token**。要让你在界面上直接看到：**每个环节累计用了多少 token，整张卡一共用了多少，并且在跑的时候随时往上涨。**

起因：你问“哪个环节耗 token 最多”，我只能翻本机 Codex 的会话记录手工拆；工具自己不记。

## 2. 你定下的口径

| 问题 | 你的选择 | 含义 |
|---|---|---|
| 显示什么 | **累计用了多少 token** | 每个环节一个累计数；整张卡一个总计 |
| 要不要折成钱 | **不要，只显示 token 消耗** | 不显示价格，不引入价格表 |

## 3. 要做成什么样（你能看到的）

1. **右栏每个环节**（写方案、写测试、写代码、复查）原来那一行写“工具 · 模型（强度）· 已干多久”，现在多一项：**“已用 N token”**。环节在跑的时候数字**随时增长**；环节结束就定格。
2. **整张卡有一个“本卡合计 N token”**，是各环节加上“备交接资料”等后台作业的总和。
3. **返工、自动退回时累计相加，不清零**：同一个环节跑了几轮，显示的是几轮加起来的总数。
4. **事后能查**：每个环节结束时，用量写进这张卡的记录里；重开应用后仍然能看到。
5. **行政**：每段对话的累计 token 显示在对话顶部（行政名字旁边）；这是**对话累计**，不是整个项目累计。
6. **读不到时老实说**：工具没给用量，或记录格式变了，就显示“—”并写原因，**不显示 0、不乱编**，也**不影响卡片继续跑**。
7. **数字怎么算**：**合计 = 输入 + 输出**（输入里包含工具重复读取的缓存部分）。详情里分项写：输入、其中缓存读取、输出。原因：缓存读取往往占九成多（比如那张真卡：写代码约 319 万里约 305 万是缓存读取），只给一个合计数会让人误以为都是“新花的”，所以详情里要把缓存单列。

## 4. 明确不做

- **不折钱，不显示价格**，不做价格表。
- **不做预算上限**（超了自动停下、提醒）。
- **不做 agy、Cursor**：你现在的团队没用它们，Cursor 我还没核实它能不能给用量，放第二版。
- **不补算历史卡**：只对新跑的卡生效；历史卡用来做对照验收（见第 5 节），不回填。
- **不做汇总统计页**（按天、按项目、按模型的汇总）。
- **不优化 token 消耗本身**：这张卡只测量，不改“写方案固定低档”这类设置。

## 5. 验收标准（具体可测）

1. **对照真实记录**：拿“流程测试带界面”那张卡的真实 Codex 会话回放，功能读出的数字必须和我手工统计的**完全一致**：
   - 写测试（Codex，gpt-6.1-sol）：**合计 2,207,607**（输入 2,178,002，其中缓存读取 2,082,816，输出 29,605）；
   - 写代码（千问，deepseek-v4.1-flash）：**合计 3,193,053**（输入 3,161,599，其中缓存读取 3,053,568，输出 31,454）；
   - 另有一个很小的 Codex 辅助会话 20,428，应归入“其他”并计入本卡合计。
2. **随时增长**：在跑的环节，数字在新一轮对话完成后更新，从界面看到的刷新延迟不超过约 5 秒；环节结束后定格不再变。
3. **返工累计**：同一环节多轮，数字是几轮之和（用多个会话的测试数据验证）。
4. **读不到时的表现**：记录缺失、格式不认识、读取出错三种情形，都显示“—”和原因，卡片照常往下走。
5. **事后可查**：环节结束后用量已写进卡片记录，重开应用后仍显示同样的数。
6. **不折钱**：界面和记录里没有价格。
7. **行政对话**：对话顶部显示本段对话累计，随每次回答增加。
8. **不拖慢**：读取只处理新增的部分，不会因为会话记录很长而变慢（用约 300 万 token 的那个会话测一次读取耗时）。
9. **测试与复查**：新增测试先红后绿；全量测试通过；真实窗口走查（跑一张真卡，看数字涨、定格、合计）；Codex 独立复查，按规范走。

## 7. 泼冷水（风险和我不确定的）

- **一个模型回合刷新一次，不是每个字刷新。** 工具写记录是一轮一轮写的，所以数字是一格一格涨。
- **依赖 Codex 内部的会话记录格式**，Codex 升级后可能变。协作包现在读 Codex 输出结尾文字也有同样风险。读不到就显示“—”，不会让卡出错，但会没有数据。
- **同时在同一个目录跑两个 Codex，容易对错号**：“备交接资料”和“写测试”就是这样，需要靠启动时间和工作目录区分，**这是最难的一点，我现在还不确定能 100% 对上**；对不上的归入“其他”，不会错记到某个环节上。
- **千问等第三方模型给的用量是它自己报的**，我已在本机 8 个千问会话里确认有记录，但**没法核对数字本身准不准**。
- **这张卡本身会花不少 token**，按上面那张卡的量级推测在 500 万以上，**这是推测**。
- **它改的是开发助手自己的代码**：应用是冻结的所以可以做；**卡在跑的时候我不碰同一个仓库**（挡路的毛病除外），做完要重装才生效，重装要你先退出应用。
- **写代码用千问，读日志格式这类活可能吃力**：所以施工单要写得准，并附真实记录的样本作为测试数据，我会盯着跑。
- **“行政对话累计”拿到的是接口返回的用量**，我读了代码确认有这个字段，**没验证过实际值**。
