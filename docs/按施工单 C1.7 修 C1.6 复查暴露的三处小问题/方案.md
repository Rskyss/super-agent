# 拆解方案

## 要做什么（一句话）
修好 C1.7 的三处小问题，让复查清单认得带方括号的写法，写方案前先读规则，并让施工方只跑本卡验收。

## 拆成几步，每步做什么、产出什么
1. 开工先读协作规则和 C1.7 施工单，再用现成的验收测试核对正式读法、兜底读法和写方案的交代分别要满足什么。
2. 在复查清单的读取代码里加一处共用处理，只对每条问题中值为字符串的级别、来源、类型去掉【】和首尾空格，包括原来紧贴括号内侧的空格，其他字段和非字符串值原样保留。
3. 正式读取确认 JSON 是对象且问题是列表后，先逐条用共用处理再做原有格式检查；兜底读取拿到问题列表后也逐条用它，正式检查仍按原有范围判定去括号后的值。
4. 在写方案的交代开头直接复用其他岗位的先读规则提醒和规则路径，确认两个模块导入时不会互相卡住。
5. 在测试命令字段说明的下一行照抄施工单的提醒「方案步骤里不要让施工方跑全部测试，全部测试由程序在复查时跑；test_command 只写本卡的测试。」
6. 如果现有验收缺少关键用例，只在新建的补充测试里覆盖两种读法、括号内外有空格以及去括号后仍不合规的情况。
7. 施工方只跑本卡验收命令并确认各组通过，程序在复查时用全部测试检查有没有新增失败；如果老测试确实需要按新口径调整，记下具体测试交给 Claude 判断。

## 你会看到什么结果
复查清单里的级别、来源、类型带不带【】都能按同一个值处理，去掉括号后仍不合规的值照旧判不合格；写方案的人会先看到读规则的提醒，并知道全部测试由程序在复查时另跑。

## 明确不做什么
不改后台进程清理、复查提示词、写方案提示词的其他内容、后续复查判断或程序自己的测试命令和跑法；不改现有测试，包括 C1.7 验收测试和已获批准的后台进程测试跳过条件。

## 需要你确认的问题
无

## 做完后怎么看结果
在开发助手的任务列表里点开 C1.7 卡片，看右侧的测试和复查结果，确认本卡验收通过，程序在复查时跑的全部测试也没有新增失败。
