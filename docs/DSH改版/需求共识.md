## 一、最高原则（用户 11-14 定）

**不重复造轮子：能改的就改，不能改的再自己造。**
- 用户是独立开发者，从零做产品的时间和额度都花不起。
- 先看 DSH（开源，MIT）和我们现有代码里有没有现成的：有就改了用；DSH 用插件扩展，插件改不了的小范围改它的源码，每处改动存成补丁文件，锁定版本、不追升级；两边都没有才自己做。
- 每个要做的东西在方案里都要写明来源：用 DSH 现成的 / 改我们现有的 / 新做（新做要说明为什么现成的不行）。

## 二、产品定位与用户

**现阶段只给用户自己用（11-14 定）**：先不考虑新用户和对外开放，不为“陌生人第一次用”设计引导和提示；等用户自己用顺了，再决定开放什么给别人。下面第 4 条里“以后给小企业用”是远期。

1. 面向普通人：用自然语言把业务问题或已有做法变成能试跑、能验收、能重复用的流程。
2. 两种起点：**有自己的做法**（如写手知道怎么找热点、搭结构、检验）/ **只有一个想法**（超级助手帮理出做法再确认）。
3. 两种工作方式：**完成任务**（提需求、做完交付）/ **持续运行**（如 24 小时盯价格）。
4. 第一个用户是用户自己（写产品、写公众号）；以后给需要用 AI 做业务的小企业用，形成收益。
5. 样板流程用正在开发的“**开发软件**”流程：做完后用新界面开发超级助手自己，边用边测。

## 三、角色分工（用户 11-14 纠正后为准）

| 角色 | 是谁 | 干什么 |
|---|---|---|
| 超级助手 | 按量付费的大模型接口（现为 DeepSeek V4.1） | 把超级助手“盘活”（配置订阅、命令行工具、能力）；和用户聊清需求、确认；判断需求类型并分流 |
| 调度员 | **订阅的命令行工具（Codex 等）或按量付费的大模型，都可以**（11-15 定） | 拿到确认好的需求，调动各种模型和 Agent 把流程做好 |
| 零件 | 知乎、小红书、高德、千问等各家命令行工具，以及接口、MCP | 被调用，办具体的事 |

- 命令行工具从来不当超级助手。

**整体流程：你只和前台对接（用户 11-14 定）**
1. 你只和超级助手（前台，即超级助手）对话；后台的调度员、积木库、能力层你一律不直接打交道。
2. 你和前台把需求聊清楚、确定下来 → 前台把确定的需求交给调度员。
3. **调度员先评审**：看这个需求和要走的流程有没有问题，有问题吐回给前台 → 前台再和你确认、改好。
4. 你最终确定（仍然是和前台确定）→ 调度员分配、组合积木库和能力层，把任务做完。
5. 做的过程中、做完之后，有事都由前台来问你、给你看结果（任务页中间的对话就是和前台的对话）。

**已定（用户 11-14）**：
- **“行政”这个概念取消，统一叫“超级助手”**（界面、文档都改；草图 24 张已改）。左栏按钮就叫“新会话”。
- **任务卡和现在的逻辑一样**：聊完，超级助手问“这是一个任务，要不要创建”，你点确认就生成任务卡，单独出现在左栏“任务”里。调度员评审（写方案、提问题）发生在**任务卡里面**，由超级助手转达给你、你批准后才开工——这和现有产品“确认建卡 → 调度员写方案给你批 → 施工”是同一套。

**已定（用户 11-15）：要配两个角色——超级助手、调度员**
- **配的时机：超级助手一开始配，调度员用到时再接**（用户 11-15 定，替代同日“两个都一开始配完”和 Claude“00c 后第一句提接调度员”的建议）：
  - 首次使用只配超级助手（00a–00e）。之后不提调度员，不加提醒条。
  - 第一次新建任务、需要开工时，超级助手才说“现在缺一个调度员，要不要接一个来做下面的任务”，你同意就走接零件那套（12/13）把调度员接上。原则：用户需要时才提示，不需要就不提示。
  - 具体落在页面上（待画图，03b/04 时一起画）：03 确认卡上加一行“还没有调度员：建卡后先帮你接一个”，让你确认前就知道；点确认照样建卡，卡里第一张就是接调度员的卡（仍然一次一张），接好后从写方案接着走。
- **超级助手**：只能是按量付费的大模型。
- **调度员**：订阅的命令行工具（Codex、agy 等）或按量付费的大模型都可以。
- **什么时候才用到调度员：任务开始干活的时候**（用户 11-15 讲清）。不开工就用不到它：
  - 造能力卡、接积木块：超级助手自己做，不需要调度员（积木块有 DSH 做 news-crawler 的实证；能力卡还没实测，开发前用 DSH + DeepSeek V4.1 按 10 页五行试做一张验证）。
  - 建任务卡：点确认建卡这一下不需要调度员；但卡里第一步“调度员写方案”就要它了（见上“任务卡和现在的逻辑一样”）。
  - 定时任务到点跑、用能力卡干活：都算开工，要调度员。
- **设置里也能加调度员**（用户 11-15 定，Claude 提的样子用户同意，06 积木库时画图）：积木库页最上面加一块“角色”——“超级助手 DeepSeek · v4.1-flash [更换]”“调度员 还没有 [接一个]”。点“接一个”跳到新会话，超级助手先开口问接哪个，走接零件流程（不另做添加表单，接入只有一种办法）；接好后显示“调度员 Codex · 已连接 [更换]”；“更换”在已接好的能干活的里挑一个，要换没接过的就回对话接。原因：调度员可能是订阅命令行也可能是按量接口，不能只靠“大脑 / 干活的”分组看出来。
- **没接调度员时确认了任务卡**：照样建卡，你的需求不丢；卡停在第一步，超级助手在这张卡里出接调度员的卡，接好了从写方案接着走。（替代之前“先出接调度员卡、不建卡”的说法。）
- **只有一个模型时复查的短板**：自己写自己查挑不出盲点，所以靠试用的真实结果 + 你最后亲眼确认，这一步不能省。
- **Claude 提醒（开发时注意）**：
  - 调度员用按量大模型时，它自己没有“手”（读写文件、跑命令），要放进一个 DSH 会话里跑——superagent 原型的执行者就是这么做的，属于用 DSH 现成的。
  - 19 改类型菜单里“接零件”的小类，原来把“调度员（订阅命令行）”当成一类零件；现在调度员是一个角色，小类应按接法分（命令行工具 / 大模型接口 / 订阅命令行 / MCP），“当调度员”是接好后指派的身份。待改图。

**还待定**：
- 调度员要不要“分配”（拆活、派给不同模型），还是一张卡交给一个执行者按固定流程走（现有产品实际是后者，见三a、三b）。
- 调度员评审适用于哪些任务（现有产品只有“干活”会写方案；接零件、造能力、搭流程要不要也先评审）。
- 接了调度员以后，能力卡、积木块是继续由超级助手做，还是交给调度员。

### 三a、调度员怎么分配：两边代码实况（Claude 11-14 读码）

**我们现有产品（以代码为准）**：
1. 超级助手出确认框前，必须凑齐四项：标题、要做什么、不做什么、怎么算做完；缺哪项就先问你（desktop/clerk/tasks.py 的 propose）。
2. 你点确认 → 立刻建任务卡 → 自动让调度员（Codex，只读、最高强度）**写方案**：一句话说明、分几步、你会看到什么、不做什么、**问你的问题（带推荐答案）**、允许改哪些文件、用什么测试（collab/planner.py）。
3. 你批准方案 → 程序按**固定顺序**施工：写测试 → 写代码 → 核对有没有改超范围 → 程序跑测试判定 → 复查 → 不过最多 3 轮 → 等你验收（collab/dispatch.py）。
4. **“分配”其实不是调度员临场决定的**：谁写测试、谁写代码、谁复查，是团队设置里事先配好的（写测试、写代码、复查三个岗位各配一个工具），程序照着排。调度员只负责写方案。
5. 现有调度员和 Codex 是长连接对话（desktop/dispatchers/codex.py，用 Codex 的官方对话接口，能看到过程、会问你“允许吗”）。

**DSH（以源码为准）**：没有单独的“调度员”角色。和你对话的那个主助手自己就是分配者，配了这几样：
- **计划模式**（packages/plan）：先探索、写计划，交给你批准再动手——对应我们的“写方案给你批”。
- **子助手委派**（packages/subagent）：可以派给同模型的分身，也可以派给 Codex、Claude Code、支持 ACP 的其他工具。但**派给 Codex 是一次性的**：不能续接、看不到进度。
- **团队任务板**（packages/team）：主助手把活拆成任务、写依赖，子助手认领或由主助手指派；依赖没完成的任务不能开始。
- **持续目标**（packages/goal）：一个会话盯一个长期目标，可自动一轮轮接着做——对应“持续运行”类任务。
- **后台任务**（packages/jobs）：长活放后台跑，做完通知。

**结论（Claude 判断，待用户看）**：
- 结构上 DSH 是“对话的人兼分配”，我们是“超级助手只对话、调度员在后台分配”，**不能照搬它的主助手**；但它的计划模式、任务板（拆任务+依赖+指派）、持续目标都可以借来给调度员用。
- 调度员本身用**我们现有的**（Codex 长连接，能看过程、能续接），比 DSH 的一次性委派强。
- 新结构里“调度员分配”= 按业务流程的步骤走，每一步用哪张能力卡、哪个零件，由流程和能力卡定好；调度员负责把它们串起来、盯进度、出问题吐回超级助手。两边现在都没有这块，要新做（现有只把“开发软件”一条流程写死在程序里）。

### 三b、DeepSeek 的 superagent 原型怎么做“调度”（Claude 11-14 读文档）

库：github.com/deepseek-ai/dsh-superagent-prototype（DeepSeek 官方组织，MIT，2.3 万星；README 写明“研究原型、仅供参考、非官方产品”，对应文章《Exploring Super-agent Design》，部分设计只是方向、未实现）。它是一个 DSH 插件包，做的是“盯着 GitHub/飞书、替团队接活写代码的机器人”。

- **两层**：主会话（代码里叫 orchestrator）只做“收消息 → 判断要不要干活 → 接单生成工单（写明可做的范围）→ 派工 → 有结果或要人决定时回话”，工具也只给这些，自己不干活；**每张工单单独开一个执行会话 + 一个文件夹**，从头干到尾，里面怎么拆、叫不叫帮手由它自己定。
- **工单状态固定几种**：等你回答 / 等你审 / 受阻 / 失败 / 排队 / 执行中 / 等新消息；面板只显示需要人处理的。
- **原则**：尽量少占人的注意力——只在被要求或规则允许时动手，只在要人决定或有结果时说话，一次只问一个具体问题。

**对我们的启发（Claude 判断，待定）**：
- 它的“调度”≈ 我们超级助手已经在做的（判断、确认、建卡）；真正干活的是每张卡背后的执行者（可以是订阅的 Codex）。所以**调度员不一定要单独成一层**：可能是“超级助手 → 每张任务卡一个执行者”，比“超级助手 → 调度员 → 各零件”少一层（11-07 调研也说角色越少越不易出错）。**用户 11-14 定：这件事后面再定，先定页面和产品结构；页面上先不画调度员这一层，任务卡右栏照实写每步用的工具。**
- 任务卡状态可借它那套，“等你处理”里再区分“等你回答 / 等你审”。
- 它自带工单引擎（存储、状态、每单一个执行会话），来源可扩展（其文档 008）；理论上可把“聊天里点确认”做成一个来源，直接用它的工单和派工。**只读了文档，没看代码、没跑过，待细看。**
- 差别：它是团队机器人、只管一个代码仓库；执行会话跑命令不经审批，和我们“安装、填 Key 要你确认”不同。

## 四、界面（用户 11-14 逐张确认）

用 DSH 的壳（界面、状态、标准交互比我们的好），按我们的产品改。

**UI 设计规则完全沿用 DSH，不自己另起一套（用户 11-14 定）**：颜色、字体、圆角、间距、浅色 / 深色主题、按钮和弹窗等基础零件、加载转圈、状态显示这些，一律用 DSH 现成的。依据在 DSH 源码里：主题和配色（packages/client/ui-theme，`--dsw-*` 那套颜色变量，支持浅色、深色、跟随系统）、基础零件（packages/client/ui-primitives）、圆角规则（docs/ui-radius）、界面评审案例（docs/ui-design-review-cases）。我们只决定“页面上放什么内容、放在哪”，不决定“长什么样”。页面草图只是示意布局，样式以 DSH 实际效果为准。

6. **左栏只放三样**：新会话（找超级助手）、“对话 | 任务”两个标签、底部设置。
