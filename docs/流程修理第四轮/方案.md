## 二、泼冷水

- **进度条的数会晚一两分钟**，而且前几分钟写代码的还没动手时一直是“0/269”。本卡测试一次要 1–3 分钟，每 2 分钟算一次，电脑会比现在忙一些。
- **“通过数”不等于“做完多少”**：有时改一处就过几十项，有时最后几项最难；它说的是“测试过了多少”，不是时间进度。
- **检测加强只能查出“接不上、带一大包说明”这类**，查不出“能接上但写得慢、写得差”；那个要看真卡。agy、Cursor 看不到用量，只做小活不看大小。
- **自动起草的“继续改”不一定对**：它是 Codex 看完几轮复查写的，你点发送前要看一眼说不说得通。每次多等 3–5 分钟，多花一次 Codex 额度。
- **复查收口有漏网的风险**：复查员可能把“这次改的”错标成“原来就有的”。所以严重的不管标什么都照样退回；“以后再修”清单在放进项目前给你看，你可以点“不满意，继续改”把它们捞回来。
- **全量搬进流程，每张卡多跑一次 13 分钟**：和复查同时跑，复查一般 4 分钟，所以复查通过后要再等约 9 分钟全量才出结果。退回几轮就跑几次。Claude 最后不再必跑全量，只抽查。
- **全量里可能有和这次无关、本来就不稳的老测试**（之前记过一项偶发超时）：照第三批的办法，只把“改之前过、现在不过”的算到这次头上。

## 三、技术设计（给下一个会话的 AI 看）

| 改动 | 落在哪 | 要点 |
|---|---|---|
| 53 进度条 | `collab/dispatch.py` 新 `_progress_thread`（照 `run_card` 起交接资料线程的写法），写 `cdir/进度.json`；`desktop/view.py` 读进 station；`desktop/static/panel.js`/`panel.css` 画条 | 写代码那步开始时起线程，步骤结束（`_dispatch` 返回）就停。每轮：工作副本里本卡测试文件（`_load_test_files`）有没有比上次新改的文件（看修改时间）；有、且离上次 ≥120 秒 → rsync 到临时文件夹（排除 .git、node_modules）→ 只跑本卡 `.py` 测试文件，`judge` 同样的超时和整组进程清理 → 从 “Ran N tests” 和 “FAILED (failures=a, errors=b)” 算通过数 → 写 `{"passed","total","time"}`。总数取“Ran N”；跑不起来（导入就报错）写 `{"error": "测试跑不起来"}`。写测试那步：数本卡测试文件里的 `def test_`，写 `{"written": N}` |
| 54 中文 | `collab/dispatch.py::_READ_RULES` 或各派活交代共用的开头 | 加一句“汇报、过程说明一律用中文大白话” |
| 55 检测小活 | `collab/check.py::check_tool`、`collab/blocks_check.py::_check_tool`/`probe_prompt` | 临时文件夹预先放 `题目.txt`（一个随机两位数）；交代：读它，加 1 写进 `结果.txt` 第一行，再运行 `ls` 把看到的文件个数写第二行；以文件内容为准（第一行 = 数+1，第二行是数字）。Codex 壳（codex、qwen）加 `--json` 时读 `turn.completed` 的 `usage.input_tokens`，超过 60,000 记 `warn`（检测仍算通，提示里写清）。版本：检测时记 `<工具> --version` 进检测记录；团队设置打开、`开跑` 前比对，不同就提醒 |
| 56 甲 起草 | `collab/dispatch.py` 复查转人工分支后；`desktop/clerk/tasks.py::_play_card_news`；`desktop/static/panel.js` 继续改框 | 转人工（cause=复查不通过）后，同一进程里再派一次“起草”：复查员的工具、最高强度、只读，交代 = 本次开工以来所有复查结论（`复查结果.md`）+ 改动文件清单 + 要求“找共同原因，写统一规则和要补的测试，开头两句大白话说为什么每轮有新问题，只写给写代码的人看的话”。记流转 `起草`（`text`=草稿文件）。行政播报“正在起草”“起草好了”。继续改框打开时，最新一条没用过的 `起草` 预填进框。起草失败只记一笔，不影响停下 |
| 57 收口 | 复查交代、`collab/flow.py`、复查 reject 分支 | 退回过以后的复查（`_review_rejects(cdir) ≥ 1` 或继续改之后）交代里加：每条在级别后标【这次改的】或【原来就有的】。程序拆条：退回的 = 严重 + 【这次改的】中等；其余写进 `cdir/以后再修.md`、流转记 `以后再修`。退回的为空 → 当作通过。连续两次退回、两次的位置（`文件`）有重叠、且第二次全是新问题（`_stop_reason` 的“同一问题”判断为否）→ 第二次的退回交代换成“先找共同原因”的写法。确认框（待验收）上方列“以后再修” |
| 58 台账 | `collab/cli.py:270`、`dispatch.py` 结束那条 summary | 写“测试没过返工 N 次、复查退回 M 次”，M = 本卡所有 `退回` 记录数 + `追加要求` 后的重开次数 |
| 59 老测试 | `_related_old_tests` | 改动里的非 .py 文件（页面、js）：在 `tests/` 下所有文件里找文件名（如 `abilities.js`）；命中的是 `test_*.py` 直接算，命中的是辅助脚本（.js、非 test_ 的 .py）→ 再找提到这个辅助脚本名的 `test_*.py` |
| 59 全量 | 复查派出前起线程，复查回来后等它 | 副本（rsync，排除 .git、node_modules、`.collab`）+ PATH 只放 python3、node 的安全目录 + `discover -p 'test_*.py'`，超时 30 分钟。复查通过、全量过 → 待验收；全量没过 → 用 `_broken_by_change` 同样的办法逐个比改之前（改之前的副本也是同样做法），只把这次改坏的当测试没过，走退回写代码的（算一次退回）；全量超时、环境出错 → 转人工。项目没有 `tests/` 或不是 Python 项目 → 跳过并记一笔 |
| 56 乙 | `docs/积木库/施工单/README.md` | 施工单检查清单加两条（出错规则四件事、拆文件把引用旧文件的老测试列进命令）|

## 四、施工方式

和前三轮一样：Claude 直接改、每条先写测试看它不过、Codex 独立复查（最多 3 轮），全量藏真工具跑。改完请你重启超级助手，开一张小卡用千问跑一遍看效果。
