# DeepSeek《Super-agent 设计探索》要点（Codex 读取整理，2026-11-04）

> 来源：https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg 。以下为 Codex 整理的摘要，**数字均为文章作者自报，未独立验证**。

1) **整体架构**

[原文](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)提出逻辑双层架构：常驻调度员 Router 负责跨信道交互、全局记忆、任务分派和跨任务协调，不执行具体工作，甚至可不配 Bash；执行者 Worker 上下文彼此隔离，配置完整执行工具，专注单项任务，内部可再建子 Agent。计算运行于云端，会话状态持久化，执行环境通过端侧 daemon 接入；独立 Watchdog 定时检查故障、任务进展及目标偏离。

2) **权限与约束怎么做的**

明确的约束主要是职责、工具配置和事件准入：程序按来源、群组、用户或机器人白名单过滤，再由模型结合提示词判断是否行动；Worker 不直接向人类回复。Router 不亲自执行可从工具层限制，但文中没有完整的权限系统设计。云端与端侧默认互信，提示词注入、设备被控制、凭据泄露仍是开放问题；白名单和提示词不能视为完整安全边界。

3) **调度员如何派活、消息如何流转**

新任务由 Router 判断并创建 Worker，随后 Worker 订阅对应 Thread（群聊话题、PR、邮件串）。已订阅 Thread 的后续事件由程序直接投递 Worker，**不经过 Router 再次转发**；Router 仍可观测全局事件。订阅是多对多关系，越界事件可退订或交回 Router。同层 Worker 通常不直接通信，通过共同订阅获知变化，少数跨任务协调由 Router 中转。关键结论回报 Router，再统一对外回复。

4) **上下文与汇报的控制方法**

采用 Inline & Spill：相关摘要、邻近内容和对象 ID 内联，长内容留在窗口外，保留续读入口；通过 Trigger—Thread—Worker 的引用图逐跳召回历史。执行细节留在 Worker，只向 Router 汇报关键结论。IM 侧低打扰、只在需要决策或验收时通知，单次回复限制为100词；PR、邮件等交付结构化详情。耗时工具异步启动，完成后以事件回注，前台可继续接收指令。

5) **实验数据**

全部性能数字均为作者自报，未构成独立验证。较有明确条件的是合成实验：约300条消息、约20个工作请求，每方案跑5次，编码用耗时工具模拟，时间间隔及工作时长缩为1/4。Super-agent 完成耗时 p50/p95 为12.4/15.7分钟，中性提示单会话 p95 为29.5分钟；取消直通后，Router 决策约增30%，读缓存 token 从2323万增至3177万，约增37%。这些支持特定负载下的调度效率判断，不能证明真实编码质量或生产收益。批处理报告1—40条/分钟、批大小1.0—2.8、请求耗时2.5—3.9秒；“单决策6.4降至1.6秒”的统计口径未充分解释。“人只能跟进3—5个会话”属于观察性自述。

6) **需要我们自己决定的地方**

需确定：授权与审批边界、凭据隔离；任务拆分与验收标准；并发写入冲突、事件去重和失败重试；汇报频率、超时与取消传播；Router 分片时机、长期记忆策略；跨实例上下文隔离及 A2A 协议。文章是架构探索，所附实现是原型，并非正式产品能力清单。
