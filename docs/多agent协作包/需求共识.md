# 需求共识：多 agent 协作包（Super-agent）

> 阶段：① 对齐 ✅（2026-11-03 与用户确认）　下一步：② 方案
> 参考：DeepSeek Harness《Super-agent 设计探索》https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg

## 一句话需求

做一个能"丢进任意项目"的协作包：**Claude 当产品负责人兼调度员，只动脑不动手；Cursor、Codex、agy 当开发和测试员**。目的是把 Claude 的额度留给最值钱的"想清楚"环节。其他几家工具的额度充足，可以多花。

## 为什么做

- 用户的 Claude Code 额度不够用，Codex、Cursor、agy 的额度富余。
- 目标是**省 Claude 的额度，不是省总消耗**。总消耗会变多（交接、各家各自读项目都要花），这一点已知并接受。

## 拍板口径（逐条已确认）

| # | 问题 | 口径 |
|---|---|---|
| 1 | 协作包放哪 | **单独新建项目**（本目录 `~/Desktop/project/super-agent`），sp2 是第一个试用项目。以后给普通人用时直接拿走 |
| 2 | 第一版分工 | **Cursor 写代码、Codex 测试、agy 先不接**，第一版跑通后再加。写和测必须是不同的两家 |
| 3 | 返工 | **全自动，最多 3 轮**。测试没过就自动退回开发修，Claude 不参与；3 轮还不过才叫 Claude |
| 4 | 第一个试跑需求 | 由 AI 从 sp2 的进度台账和遗留问题里挑 3 个候选（小、能自动验收），用户选一个 |

## 沿用前期讨论已定的原则

1. **Claude 在权限上就改不了产品代码**，只能写协作区里的文件，不靠自觉（文章实验：只靠提示词约束，主模型会自己上手干活）。
2. **验收标准必须能自动判断对错**。用户说不具体的地方，由 Claude 翻译成可检查的标准，再拿回来让用户用大白话确认。
3. **"过没过"由一段固定程序判断**，不让 AI 判断。
4. **开发交活写 100 字以内的汇报**，详细改动留在原处。Claude 只读需求卡、汇报、测试结论这三样。
5. **每个开发在自己的项目副本里干活**，验收通过后才合并；要改同一块地方的两张卡排成先后。
6. **只在 5 种情况下叫醒 Claude**：返工超 3 轮；开发或测试员说需求卡看不懂；合并后冲突；干了很久没进展（超时）；中途发现需求本身要改（这种还要回来问用户）。
7. **动手前自动存一个版本**，出事能一键恢复。
8. **两道人工关口**：开头用户确认需求卡，最后用户看实际效果。上线、推送由用户决定。

## 明确不做（第一版）

- 不接 agy（备用）
- 不放到云端常驻运行，不监听群聊、不主动揽活（文章里团队规模的部分）
- 不做自动推送或上线
- 产品化功能（自动检测用户装了哪些工具、插件式一键安装、面向普通人的引导）**第一版不做**，但设计上不能把路堵死

## 怎么算验收通过

1. 在 sp2 用一个真实的小需求，从"写需求卡"到"合并"全程跑通，**期间 Claude 没改过产品代码**。
2. 至少发生过一次"测试没过 → 自动退回 → 修好"，并且全程没经过 Claude。
3. 用户能在任务板上看懂每张卡现在在哪一步、谁在做、返工了几次。
4. 有一份 Claude 额度消耗的对照记录。**怎么量还没定**，在方案里提出测量办法，由用户确认。

## 已知风险（提前说）

- 磨合期需求卡难免写得不细，Claude 会经常被叫醒，省额度的效果要几轮之后才显现。
- 省下多少额度目前是推测，必须以实测为准。
- 探索性需求、大的架构调整不适合拆出去，硬拆返工更多。
