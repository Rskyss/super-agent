## 数字

干活合计 57 分钟、约 1858 万 token；写测试 5 次（约 470 万）、写代码 3 次（约 1013 万）、复查 3 次（约 372 万）；复查退回 2 次后转 Claude 接手，接手后 Codex 又复查 2 轮。

## 问题出在哪（按影响大小）

1. **施工单把“记住停在哪”写简单了（Claude 自己的问题，影响最大）**
   三轮复查退回的十几条，几乎全落在同一块：加载先后（列表先回还是卡先开）、主对话的字和卡片对话的字共用一个输入框、切到一半又切走、退出时补存。施工单只写了“存 thread/card/draft、切回恢复”，没写“看卡时主对话的字归谁管”“页面没加载完时报什么”。写代码的只能边被退回边猜。
   → **调**：以后凡是“记住状态、切回恢复”这类功能，施工单里先列一张“什么时候、谁的东西、存什么、恢复成什么”的表，把加载中、看卡中、删除后这几种情况写死，再交出去。

2. **复查员把“加载空档里才出的问题”标成“少见·严重”，程序照退**
   程序的规矩是“极巧合不退、少见只退严重的”。复查员把“页面加载那一两秒里又点了别的”这类问题标成“少见”而不是“极巧合”，又标“严重”，于是一轮轮被退回，写代码的为了修它们还改坏了原来的设置页。
   → **调**：给复查员的说明里把“极巧合”写具体：“只在加载、切换的一两秒空档里连续操作才出的”算极巧合。只改说明文字，不改判定。

3. **写代码的为了过复查，改了原有功能和无关样式**
   第 2 轮为修“停用行政时恢复卡”，把“进团队设置页收起右栏”这条老行为改掉了；还顺手把左栏一排旧样式换了颜色。施工单写了“只按施工单做”，没挡住。
   → **调**：给写代码的退回说明里加一句：“修退回的问题如果要改动原来就有的行为（不是这次新加的），停下不改，写进汇报”，让它交给 Claude 判断。

4. **写测试的大量用“逐字比对代码”的检查**
   很多检查是“代码里必须出现某某写法”。它们一是挡不住真错（Codex 两次证明把代码写坏了检查照样过），二是把错误做法也钉死了（“停用行政恢复卡”的三条检查逼着写代码的往错的方向改）。项目里其实有现成的“真的把页面脚本跑起来”的检查工具，这次 Claude 接手后用它补的 8 段检查，逐处去掉修复都能抓到。
   → **调**：写测试的说明里加：“页面上的行为，优先用实跑页面的检查（tests/ability_69b_dom.js 那套），逐字比对代码只用在没法实跑的窗口外壳上。”

5. **卡停下时程序给的建议是错的**
   停卡时写“复查说测试本身写错了……建议点‘不满意，继续改’”，实际是复查到顶、该人接手。用户差点照着点。
   → 并入小修第 2 条一起看：停下时的那段话要说对“为什么停、该谁动”。

6. **Claude 让用户点“接受”前，没先把已知要改的老测试在副本里改好**
   Claude 自己跑全量时已经看到那条老测试要变，却等用户点了“接受”、程序跑 4 分钟失败后才改，用户多点了一次、多等了 4 分钟。
   → **调（Claude 自己）**：接手的卡，交给用户点“接受”之前，先在副本里把全量跑绿。

## 不调的

- 窗口外壳（Swift）只能逐字检查、靠真实窗口走查：结构如此，代价大，不动。
- 放进项目只收允许范围内的文件、漏带的会提醒：这次提醒了，Claude 补了，规矩够用。
- 千问写代码、GLM 写测试、Codex 复查这套组合：这次的问题不在模型能力，在 1–4 条，先不换。
