# 多模型协作写代码：调研

**状态：** 📚 调研资料，不是需求。2026-11-07 用户问“大家是多个模型协作写代码，还是一个模型写”，要求查文献、报道，并给出判断。

## 一、结论

1. **主流是多模型，但只有少数几种分工被证明有用。** 有用的有三种：
   - 一个写、另一个复查；
   - 测试由写代码以外的人来写；
   - 强模型出方案、便宜模型照着做。
   “模拟一家软件公司、多个角色一起干”这种做法，研究里失败率很高。
2. **同一时间只让一个人动手改。** 别人可以出主意、挑毛病，但不同时改。（Cognition 2026 年的结论）
3. **复查必须换人。** 模型给自己打分会偏高，自己查自己基本没用。换一家模型查更好，但不同家的模型也常错在同一个地方，所以复查还要真跑测试、真走流程。
4. **方案的质量决定结果。** 方案错一处，后面的代码会成片错。谁写方案，谁就决定上限。执行的人主要影响花多少钱。
5. **交接不能太多。** 每交接一次就丢一点信息。查原因、修疑难问题这类要通盘想的活，一个模型从头做到尾更好。
6. **方向有讲究。** 强的查弱的有用，弱的查强的可能把对的改错。

## 二、证据（按可信度排）

### 论文和大规模实测（可信度高）

| 来源 | 发现 | 对我们的意思 |
|---|---|---|
| Why Do Multi-Agent LLM Systems Fail?（NeurIPS 2025，arxiv.org/abs/2503.13657） | 7 个多 AI 协作框架失败率 41%–87%。模拟软件公司的 ChatDev 在他们的测试集上只有 33% 做对。失败主要有三类：不按要求做、角色之间对不上、没人认真检查 | 角色越多，越容易出错。不要靠多加角色提高质量 |
| LLM Evaluators Recognize and Favor Their Own Generations（NeurIPS 2024，arxiv.org/abs/2404.13076） | 模型能认出自己写的东西，并给它打更高分 | 写的人不能自己验收 |
| Correlated Errors in LLMs（ICML 2025，arxiv.org/abs/2506.07962） | 比了 350 多个模型：两个模型都答错时，60% 错成同一个答案。越强的模型越像，不同公司的也一样 | 换一家模型查有用，但不能代替真跑测试 |
| AgentCoder（arxiv.org/abs/2312.13010） | 测试由单独的角色写，测试准确率 89.6%，对照组是 79.3% | 测试和代码分开写，这条我们已经在做 |
| Cross-Model LLM Code Review（2026，arxiv.org/html/2607.21656v1） | 116 道编程题：Codex 写、Claude 查，正确率 72%→90%；Claude 自己查自己，没有变化；Claude 写、Codex 查，91%→83% | 谁写谁查的方向会影响结果。局限：做的是算法题，复查方不能跑测试，用的是旧模型 |

### 厂商工程报告（可信度中，有自家立场）

| 来源 | 发现 |
|---|---|
| Anthropic《How we built our multi-agent research system》 | 一个总负责加多个帮手，做资料调研比单个模型好 90%，但花的额度多得多。报告也说，写代码能拆开并行的部分比调研少 |
| Anthropic《Building effective agents》 | 先用最简单的办法，不够用了才加多 AI 协作 |
| Cognition《Don't Build Multi-Agents》（2025-06） | 多个 AI 同时动手，会各自做出互相冲突的决定 |
| Cognition《Multi-Agents: What's Actually Working》（2026-04） | 现在能用的做法是：只有一个人动手改，其他人出主意、挑毛病。不带包袱的复查员能看出写的人看不见的问题。主力模型太弱时，叫强模型帮忙也救不回来，主力决定上限 |
| Aider 架构师/编辑模式（2024-09） | 推理强的模型出方案、另一个模型改文件，当时拿到 85% 的最好成绩 |

### 个人实测和社区经验（可信度低，只作参考）

- Morph：40 个真实应用，比了 44 种“出方案＋执行”组合。执行用便宜模型，执行那部分花费降到约四分之一。这家公司卖相关产品。
- Quesma：4 个模型组队，花费主要看执行的人；交接 3 到 5 次时九成能成，6 次以上只剩一半。只是一个人的实验。
- Reddit r/LangChain：有一次排查问题的任务，单个模型比多个模型分工便宜 10 到 20 倍，而且只有它答对。
- Reddit r/vibecoding、r/ClaudeCode：常见用法是 Claude 写、Codex 查，或者反过来。用户的说法是 Claude 爱设计得复杂，Codex 爱走捷径，正好互相挑。

## 三、对照我们的做法

**已经对上的：**
- 一次只让一个人动手写：Cursor 写，或者我写。
- 测试和代码分开写：我写测试，Cursor 不许改。
- 有独立复查，还在真实窗口里实际走一遍。
- 有方案和施工单。

**有缺口的：**

1. **我在验收时自己改、自己验。** 这批两个最严重的问题，都是我验收时自己修出来的，正好是“自己查自己”。规矩：谁改的，就换另一个人查。我改的代码，最好交给另一家的模型查，比如 Codex。
2. **施工单写得薄的地方，Cursor 就自己发挥。** 这对应“方案的质量决定结果”。施工单要把容易做歧的地方写死。
3. **复查轮数要有上限。** 这批跑了三轮，还在合理范围内。再往上走，交接太多，成功率反而会掉。

## 四、关于“让 GPT-6.1-Sol 写方案、Claude 执行”

- 研究支持“写方案的位置最要紧”，所以这里该放最强、最懂这个项目的模型。
- 没有任何公开对比测过 GPT-6.1-Sol 和 Claude Opus 5.5 谁更会写方案。2026 年那篇论文是旧模型做算法题，不能直接套用。
- Cognition 发现主力模型的关键能力是知道该问什么、什么时候该求助。对一个不看代码的产品经理来说，问对问题、用他听得懂的话说，比会写代码更重要。
- 判断方法：拿一个真实需求，两边各自独立写需求共识和方案，去掉署名后由用户比较。

## 五、对超级助手产品本身的启示

- 现在的分工（行政、测试员、开发员、复查员）方向是对的，但角色不宜再加。MAST 研究说明，角色多了失败会变多。
- 复查员换一家模型来做是有依据的，但复查必须能真跑测试，不能只看代码。
- 小需求可以少几道交接。这和《讨论记录》里的“快速档”想法一致。
