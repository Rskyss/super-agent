# 按需求大小调配角色：讨论记录

**状态：** 💡 只是讨论，用户没有提需求，也没有批准开发。用户再提这个需求时，先读本文，不用从头聊。

**日期：** 2026-11-06

## 用户的想法

- 超级助手聊清需求后，能不能判断这是小需求、中需求还是大改动，再决定怎么调配角色。
- 用户明确说这是讨论，要 Claude 以 PM 的身份一起判断。
- 行政像产品经理：不看代码也能弄清需求，只管产品有哪些功能、实现了哪些、好不好做。

## 为什么值得做

现在每张卡不分大小，都走 Codex 写测试、Cursor 写代码、程序判定、agy 复查。实测“加一个减法函数”真实跑一遍也要 5 到 8 分钟（314 到 506 秒），动用三个工具。

## 讨论出的判断

这些是 Claude 的判断，用户说“大概明白了”，还没有拍板，也没有实测。

**分档：** 先只分“快速”和“完整”两档。三档边界说不清，分错了用户也不好判断。

| 档 | 谁来做 |
|---|---|
| 快速 | 开发员写代码，程序跑测试，复查员对照需求检查。省掉测试员 |
| 完整 | 现在的完整流程 |

- 不能只留“写代码 + 跑测试”：没有测试员就没有新功能的测试，程序只跑旧测试，新功能写错也可能显示通过。用户不看代码，这样等于没人检查。
- 快速档能抓到多少问题还不知道，要真实跑过才算数。

**谁来判断：**

| 谁 | 负责什么 |
|---|---|
| 行政（DeepSeek） | 像 PM 一样聊清需求，给粗略判断，把建议说给用户听 |
| Codex（写方案时） | 像工程师一样看代码，列出实际要改的文件和影响 |
| 程序 | 按固定规则出“快速”或“完整”的建议 |
| 用户 | 看一句建议，点确认或换一档 |

- 不用调度员：配了行政后调度员已经不干活，再请回来只会多花钱、多一层传话。
- 弄清需求不用看代码；确认改动范围要看代码。行政和 Codex 对不上时，以 Codex 为准，并告诉用户为什么变了。
- 行政好不好用，很依赖《项目说明》和台账写得清不清楚。

**硬规矩：**

- 只能往严里调：碰钱、数据、删除、安全的改动，程序直接走完整，模型不能调低。
- 快速档也要真跑测试，超出范围仍要拦下。中途发现不止这些文件，就停下问用户要不要升级。
- 刚开始只给建议，不自动决定。攒够真实记录，确认判断准不准，再谈放开。

**风险：** 判小了会少一道检查，问题可能漏到验收时才发现。

**优先级：** 排在合并和每卡对话之后。还没走通合并时，提速解决不了主要问题。

## 重新提起时要先定的事

1. 用户平时的需求，有多少是“改几个字、调个样式”这种小活？超过一半可以排到排队接力前面，多数是跨功能改动就再往后放。（用户还没回答）
2. 用几张真实卡片验证：Codex 列的文件准不准。
3. 同一个中等需求，用单模型和超级助手各做一遍，比较返工次数、额度和验收时发现的问题。超级助手是否一定更好，现在没有对比数据。
